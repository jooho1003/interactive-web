# 전시관 레이어 배포 저장 계획

2026-10-05 · bkit Plan · 사용자 요청: 배포해도 수정 배치 유지.

## Executive Summary

| 관점 | 내용 |
|---|---|
| 문제 | 브라우저 저장값은 Git과 배포에 포함되지 않는다. |
| 해결 | 로컬 저장 버튼으로 public/layers.values.json을 갱신하고 배포에서 읽는다. |
| UX | 저장 위치를 안내하고 새 방문자도 저장된 배치를 본다. |
| 가치 | 눈으로 수정한 결과가 실제 배포 기본값이 된다. |

## 1. 참고 및 원칙

docs/00, docs/10, docs/11 §7, 앱 README·QA를 읽었다. 값 파일과 매니페스트를 분리하고 기존 layerHost 검증/범위 해석을 재사용한다. 외부 상호작용 레퍼런스는 해당 없음. 새 에셋·시각 디자인·다른 작품 저장 방식은 이번 범위에 필요하지 않다.

## 2. 범위와 요구사항

- 현재 연결 탭의 JSON을 먼저 내보냈다. 현재 값은 빈 override이며 해당 키의 localStorage도 null이다. 사용자는 Chrome에서 편집했다고 답했다. 해당 Chrome은 디버깅 연결이 없어 직접 읽지 못했으며, 기존 로컬 저장본 이관을 지원한다.
- 기존 로컬 저장본은 로컬 편집 환경에서 읽어 보존한다. 저장은 프로젝트 파일을 갱신한다.
- 배포에서는 정적 값 파일이 기본값이다. 이전 배포의 브라우저 초안은 새 게시본을 덮지 않는다.
- 정적 배포에서 저장한 초안은 브라우저에만 유지되며 UI에서 정확히 안내한다.
- 실제 게시/커밋/push는 사용자 요청 범위가 아니다. 값 파일을 커밋·배포할 수 있게 구현한다.

## 3. 순서와 성공 조건

1. 저장 파일 및 초기 읽기 구현 → 검증된 iw-layers/1 파일이 빌드에 포함.
2. 로컬 API와 저장 UI 연결 → 파일 저장 성공에만 게시용 저장 완료, 실패는 미저장 유지.
3. 임시 디렉터리 API 테스트와 분리된 브라우저 검수 → 새 방문자 적용, 범위 보존, 실패/충돌, 모바일/Ctrl+S 확인.

## 4. 영향과 위험

gallery spatial-layers/editor, preview-spatial, 앱 check에만 변경한다. village의 기존 저장은 유지한다. QA는 API를 격리해 실제 배치 파일을 덮지 않는다. 로컬 API는 loopback 및 동일 Origin 제한, 고정 파일 경로, 크기/매니페스트 검증, 원자적 쓰기, revision 충돌 확인을 둔다.
