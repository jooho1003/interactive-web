## 1. 아키텍처 패턴 비교: clone-per-project vs 멀티테넌트 vs 헤드리스 CMS vs 플랫폼화(SaaS)

### (a) 프로젝트마다 복제 (clone-per-project) — 강연자(김그륜) 방식
- 각 클라이언트/작품마다 베이스 앱(관리자 포함)을 통째로 fork/clone해서 독립 배포.
- **장점**: 프로젝트별 완전한 격리, 클라이언트별 커스터마이징 자유도 최대, 장애가 다른 프로젝트로 전파되지 않음, 계약·호스팅을 프로젝트 단위로 딱 떼어 넘기기 쉬움.
- **단점**: 업스트림(베이스 템플릿) 개선사항을 이미 나간 N개 클론에 일일이 다시 적용해야 함 — 수작업이면 유지보수 비용이 프로젝트 수에 비례해 선형 증가. single-tenant/커스텀 개발은 초기 비용이 높고($100K~1M+ 언급되는 수준의 대형 SaaS 사례 기준이긴 하나 원리는 동일) 반드시 상시 관리 인력이 필요하다는 지적이 있음.
- **적합 규모**: 작품 수가 적고(수개~십수 개) 각각의 커스터마이징 폭이 크며, "그때그때 클라이언트 요구에 맞춰 확 바꿔야 하는" 전시/캠페인성 프로젝트. 정확히 강연자의 8개 동시 운영 사례가 이 상한선 근처.

### (b) 멀티테넌트 단일 코드베이스 + 테넌트별 설정 (White-label)
- 하나의 앱이 여러 테넌트(클라이언트)를 설정값/테마로 분기해서 서빙.
- **장점**: 업데이트를 한 번 배포하면 전 테넌트에 즉시 반영 — "updates deploy once, not per customer". 인프라 공유로 비용 절감(사례: 하이브리드 멀티테넌트 전환 후 인프라 비용 $45,000/월 → $10,000/월, 78% 절감, 6개월 마이그레이션). 운영 오버헤드가 테넌트 수 증가에 비례해 늘지 않고 평탄하게 유지됨.
- **단점**: 초기 아키텍처 설계 난이도 높음(테넌트 격리, 커스터마이징 한계), 한 테넌트의 특이 요구가 코드 전체에 조건분기로 누적되면 복잡도 증가("커스터마이징 부채").
- **적합 규모**: 수십~수백 개 이상의 프로젝트를 운영하며 개별 커스터마이징 폭이 제한적(설정 가능한 범위 내)일 때. 유지보수 예산은 일반적으로 SaaS 원가의 연 15~25% 수준을 매년 잡는 것이 권장됨(의존성 업그레이드, 보안 패치, 마이그레이션, 버그 수정 포함) — 이는 테넌트당이 아니라 전체 시스템 기준이라 테넌트가 늘수록 테넌트당 유지보수비는 급감.

### (c) 헤드리스 CMS + 템플릿 프론트
- 콘텐츠(텍스트/이미지/설정)는 헤드리스 CMS(예: Notion-as-CMS, Storyblok, Contentful, DatoCMS)에, 프론트는 정적/템플릿 코드로 분리.
- 에이전시들이 2026년 들어 "static-first + headless CMS" 패턴으로 다수 클라이언트 사이트를 표준화하는 흐름이 뚜렷 — Next.js/Astro/Nuxt 같은 정적 우선 프론트에 콘텐츠 API를 붙이는 방식.
- DatoCMS는 "Agency plan"으로 여러 클라이언트 사이트를 한 계정에서 관리하는 것을 공식 지원(템플릿화된 사이트 빌드를 다수 클라이언트에 반복하는 에이전시에 최적). Cosmic은 클라이언트별로 격리된 "bucket"(프로젝트) 구조 제공. Storyblok은 비주얼 에디터를 클라이언트가 직접 쓸 수 있게 하는 데 강점.
- **장점**: 콘텐츠 수정 권한을 클라이언트에게 안전하게 위임 가능(코드 접근 없이) — "관리자 페이지 = 클라이언트 소통 레이어"라는 강연자의 패턴과 정확히 일치. 프론트 코드는 여러 클라이언트가 공유하므로 업스트림 개선이 코드 배포만으로 전파됨.
- **단점**: 콘텐츠 스키마가 테넌트마다 달라지면(3D 포탈 갤러리 vs 월드게임 vs 뉴스레터 플랫폼처럼 장르가 다르면) 단일 CMS 스키마로 묶기 어려워짐 — 결국 "장르별 템플릿 패밀리 + 장르별 CMS 스키마"의 조합이 필요.
- **적합 규모**: 콘텐츠 편집이 잦고 구조가 어느 정도 정형화된 브랜드 플랫폼류(뉴스레터·예약·후원)에 특히 적합. 3D 포탈 갤러리나 분기형 AI 영화처럼 구조 자체가 매번 달라지는 장르에는 헤드리스 CMS보다 (b)+(a) 하이브리드가 나을 수 있음(미확인 — 실제 구현 사례로 검증 필요).

### (d) 플랫폼화 (SaaS: 사용자가 직접 만듦)
- 최종 사용자가 직접 템플릿을 골라 편집(예: Framer, Webflow, Spline, Readymag 모델).
- Framer는 프로토타이핑 툴에서 출발해 스크롤 이펙트·페이지 전환·3D 트랜스폼·마이크로 인터랙션을 "1급 시민 프리미티브"로 다루는 것이 강점으로 꼽히며, 디자인 주도 팀의 Webflow 대체재로 자리잡음. Webflow는 콘텐츠 중심 마케팅 사이트의 성숙한 CMS 플랫폼. Readymag은 에디토리얼/매거진형 디자이너를 타깃. Spline은 3D 디자인 툴 자체(웹사이트 빌더는 아님)로 커뮤니티 템플릿을 리믹스하는 구조.
- **장점**: 유지보수 부담이 플랫폼사에 집중되고, 제작자는 템플릿 판매/구독 매출만 관리하면 됨. 확장성 최고(수천~수만 사용자).
- **단점**: 플랫폼 자체를 만들고 운영하는 것 자체가 별도의 거대한 사업 — "인터랙티브 웹을 양산하는 툴"을 자체 SaaS로 완전 개방하려면 에디터 UX, 과금, 호스팅, 템플릿 심사 등 전혀 다른 제품을 만들어야 함.
- **적합 규모**: 장기적으로 수천 개 이상 규모를 노릴 때만 정당화됨. 현재 프로젝트(모노레포 + 템플릿 제너레이터로 "다양한 장르 양산")는 (a)+(c)의 하이브리드에 더 가깝고, (d)는 3~5년 후 확장 옵션으로 고려할 단계로 보임.

### 결론 (아키텍처 권고, R5 관점)
장르별 템플릿 패밀리가 이미 고정되어 있고(3D 포탈 갤러리/월드게임/분기형 영화/브랜드 플랫폼/루틴 앱) 각 장르 내에서는 구조가 비슷하다는 점을 고려하면:
- **모노레포 + 패키지화 + 장르별 "clone 시점의 템플릿 버전 고정"**이 현실적 절충안. 즉 (a)의 격리성 + (b)의 업데이트 전파 이점을 부분적으로 취하는 방식 — 공용 패키지(코어 엔진, 관리자 UI 컴포넌트, 분석 SDK)는 semver로 배포하고, 개별 프로젝트는 그 패키지의 특정 버전을 고정해서 쓰다가 필요할 때만 업그레이드.
- 관리자 페이지(콘텐츠/문구/날짜/발송)는 헤드리스 CMS 패턴(c)을 차용 — Notion 미러링 또는 자체 경량 CMS로 클라이언트에게 안전한 편집 권한만 위임.

## 2. 템플릿 갱신 전파 — 실제 오픈소스/스타트업 사례

- **Changesets**(npm, `@changesets/cli`): 모노레포에서 각 패키지 변경사항을 "changeset" 파일로 선언 → 자동으로 버전 범프·체인지로그 생성·퍼블리시. `updateInternalDependents` 설정으로 내부 의존 패키지까지 연쇄적으로 버전이 올라가도록 강제 가능 — 한 패키지가 오래된 내부 의존성을 참조하는 상태를 방지. GitHub Actions와 연동해 main 브랜치 푸시 시 자동으로 버전 판단·체인지로그 생성·npm 퍼블리시하는 파이프라인이 표준 패턴.
- **Polyglot 모노레포**: changesets는 기본적으로 package.json 버전을 올리는 도구이므로, Python/Go 등 다른 언어 패키지가 섞인 모노레포에서는 changesets가 올린 버전을 해당 언어의 메타데이터 파일에 다시 전파하는 커스텀 스크립트가 필요.
- **DB/설정 스키마 마이그레이션(멀티테넌트 SaaS 관점, 직접 유사)**:
  - pgroll(오픈소스, Postgres): 무중단·가역적 스키마 마이그레이션 — 마이그레이션 기간 동안 신/구 스키마를 동시에 서빙해 앱 다운타임 없이 전환.
  - 테넌트별 스키마 버전을 중앙 레지스트리에 기록하고 마이그레이션 이력/상태를 테넌트 단위로 추적(Bytebase, Liquibase 등 도구 활용).
  - **단계적 롤아웃(staged rollout)이 정석**: 카나리 테넌트 → 무료 테넌트 전체(병렬 최대 10개) → 유료 테넌트(제어된 병렬도) 순으로 확산. 에러 발생 시 나머지 테넌트는 계속 진행하는 "에러 내성(error resilience)" 설계 권장.
  - 스크립트는 `IF NOT EXISTS` 등으로 **재실행 안전(idempotent)**하게 작성, 트랜잭션으로 원자성 보장, dev/staging에서 먼저 검증 후 일부 테넌트에 카나리 배포.
- **코드무드(codemod)**: 검색 결과에서 코드무드 자체에 대한 1차 사례는 명확히 확인되지 않음 — jscodeshift류 도구로 "패키지 API가 바뀌면 사용처 코드를 자동 변환"하는 것이 업계 일반 패턴이라는 것은 상식 수준이나, 이번 조사에서 인터랙티브 웹 템플릿 맥락의 구체 사례는 **(미확인)**.
- **적용 제안**: 코어 패키지(3D 엔진 래퍼, 관리자 UI kit, 분석 SDK)는 changesets로 semver 관리 → 각 클론 프로젝트는 `package.json`에 정확한 버전 고정 → 업그레이드 시 "설정 마이그레이션 스크립트"(예: `migrate-config.js vX→vY`)를 프로젝트별로 1회 실행하는 방식이 오픈소스 관례와 가장 정합적.

## 3. 수익화·시장

### 3-1. 인터랙티브 웹 제작 단가

**해외(글로벌 WebGL/Three.js 스튜디오)**
- Utsubo(WebGL/Three.js/WebGPU, BMW·Louis Vuitton·Warner Music 클라이언트 보유, FWA/Awwwards 수상) — 기본 견적 **$20,000부터 시작**.

**국내 — 일반 홈페이지 제작(비교 기준선)**
- 단순 구조(소개+서비스+문의): 200만~400만 원.
- 맞춤 디자인형: 150만~200만 원대.
- 기능 위주 시스템형(쇼핑몰/예약/커뮤니티): 200만 원 이상.
- 고정비(호스팅+도메인+SSL): 월 2.5만~5만 원.
- ※ 이 가격대는 "인터랙티브/3D 요소"가 포함되지 않은 일반 반응형 홈페이지 기준이며, 인터랙티브·SEO 고도화·특수 개발이 들어가면 별도 가산된다고 명시됨(구체 인터랙티브 가산액은 **미확인**).

**국내 — 미디어아트/전시 인터랙티브 설치(프로젝션 매핑 등, 크몽 기준 — 참고용, 정가 협상 시장)**
- 최저 10만 원 ~ 평균 약 100만 원 ~ 최고 230만 원 이상.
- 프로젝션 매핑 패키지 예시: STANDARD(20초 루프, 5일) 60만 원 / DELUXE(30초 스토리 없는 루프, 10일) 210만 원 / PREMIUM(스토리 포함, 러닝타임 협의, 30일) 600만 원.
- 가격 변수: 설치 규모, 인터랙션 포함 여부, 하드웨어 포함 여부, 전시 기간(장비 임대비 비례).
- ※ 이 가격대는 "영상+공간 연출" 중심이며, 웹 기반 3D 포탈 갤러리/분기형 인터랙티브 웹 프로젝트의 단가와는 결이 다름 — 웹 기반 견적은 **미확인**(국내 사례를 직접 찾지 못함).

## 4. 클라이언트 워크플로우

### 4-1. 관리자 페이지를 납품물로 쓰는 계약 구조
- 헤드리스 CMS 업계에서 "전통적 CMS는 히어로 이미지 교체/블로그 등록/팀 페이지 수정 같은 일상적 업데이트조차 개발자 의존을 만든다"는 점이 핵심 페인포인트로 지적됨 — 관리자 페이지를 클라이언트에게 넘기는 것은 이 의존을 끊는 명확한 가치 제안.
- Storyblok류는 "코드 구조와 무관하게 클라이언트가 쓸 수 있는 비주얼 에디터"를 강점으로 내세움 — 계약서에는 (1) 관리자 접근 권한 범위(콘텐츠 편집만 vs 구조 변경까지), (2) 유지보수 책임 소재(호스팅 장애/보안 패치는 누구 담당), (3) 호스팅 비용 전가 방식(클라이언트 명의 vs 에이전시 명의로 대납 후 청구)을 명시하는 것이 표준 관행으로 보임(구체 계약 조항 예시는 **미확인**).

### 4-2. 미리보기/승인 흐름
- 검색 결과에서 인터랙티브 웹 특화 미리보기/승인 워크플로우의 1차 사례는 확보하지 못함 **(미확인)**. 일반 CMS 업계에서는 "draft → in review → approved → shipped" 상태값을 가진 Deliverables 데이터베이스(Notion 등)로 승인 흐름을 관리하는 것이 일반적 패턴으로 확인됨(아래 4-3 참고).

### 4-3. 데이터 소유권 (Notion 미러링 등)
- Notion을 클라이언트 포털로 쓰는 패턴이 명확히 존재: 내부 태스크를 클라이언트 대시보드에 "미러링"하면, 상태/기한 업데이트가 양방향 동기화됨. Notion을 헤드리스 CMS로 전환하는 오픈소스 도구(`agency-kit/notion-cms`, GitHub)도 존재 — Notion을 콘텐츠 소스로 쓰고 프론트는 별도 코드가 렌더링하는 구조가 실제로 구현되어 있음.
- 데이터 소유권 이슈: 클라이언트가 Notion 워크스페이스를 소유("client-owned Notion")하는지, 에이전시 워크스페이스에 게스트로 초대되는지에 따라 계약 종료 시 데이터 이전 가능 여부가 갈림 — 계약서에 "Notion 워크스페이스 소유권은 클라이언트에게 귀속되며 에이전시는 편집 권한만 가진다"는 조항이 필요.

### 4-4. 재사용 코드의 IP 문제
- 가장 핵심적인 발견: **"work for hire" 조항은 미국 내에서는 대체로 IP를 클라이언트에게 이전시키지만 국제적으로는 무너진다** — 해외(비-미국) 클라이언트와의 계약에는 명시적 IP 양도 조항이 별도로 필요.
- **템플릿 재사용 보호의 핵심 관행**: "에이전시/컨설턴트/플랫폼 개발자는 다른 클라이언트를 서빙하기 위해 자체 프레임워크·라이브러리·방법론에 대한 권리를 정당하게 보유해야 한다. 포괄적(blanket) IP 양도는 이를 침해하므로, 커스텀 결과물만 클라이언트에게 완전 귀속시키고 재사용 가능한 툴은 별도로 보존하는 carve-out(제외) 조항을 협상해야 한다."
- 즉 계약서에 **"본 프로젝트에 사용된 베이스 템플릿/엔진/컴포넌트 라이브러리는 [에이전시명]의 소유이며, 클라이언트는 최종 산출물(콘텐츠·커스터마이징·디자인)에 대한 라이선스만 취득한다"**는 명시적 제외 조항이 없으면, 템플릿 자체가 실수로 클라이언트 소유물이 되어 다른 프로젝트에서 재사용이 막힐 위험이 있음.
- 실무 리스크: "직원용 계약서 문구가 그대로 프리랜서/외주 계약서에 복붙되면서 고용 형태 오분류(misclassification) 리스크가 조용히 유입되는 경우가 흔하다"는 지적 — 계약서 템플릿을 재사용할 때도 각 계약 유형에 맞게 조정 필요.

## 5. AI 생성 에셋의 법적·정책 이슈 (2026 기준)

### 5-1. 저작권 — 미국
- 2026년 3월 미국 연방대법원이 Thaler v. Perlmutter 관련 상고를 기각하며 하급심 판결이 확정 — **순수 AI 생성 콘텐츠는 인간 저작성(human authorship) 요건을 충족하지 못해 저작권 보호 대상이 아니다**는 원칙이 현행 판례로 굳어짐.
- Midjourney: 유료 구독자는 산출물에 대한 폭넓은 상업적 이용 라이선스를 받지만, AI가 생성한 부분 자체의 저작권을 주장할 수는 없음(선택·편집·프롬프트 엔지니어링으로 더한 창작적 부분만 보호 가능). 연 매출 $1M 이상 기업은 Pro 플랜 이상 구매가 상업적 이용의 조건. 공개 이미지는 타인이 리믹스 가능하고, 콘텐츠·프롬프트에 대해 Midjourney에 영구·무상 라이선스를 부여하게 됨.
- **면책(indemnification) 부재**: Runway, Midjourney, Suno, ElevenLabs, Stable Diffusion 모두 일반(소비자) 플랜에서는 제3자 저작권/상표권/퍼블리시티권 침해 클레임에 대한 면책을 제공하지 않음 — "직접 책임을 진다"는 의미. 기업 플랜에서 면책 조항이 추가되는지는 도구별로 확인 필요(**미확인** — 모델별 상세 비교는 추가 조사 필요).

### 5-2. 저작권 — 한국
- 한국 저작권법상 저작물은 "인간의 사상 또는 감정을 표현한 창작물"로 정의 — AI가 완전 자동 생성한 이미지는 원칙적으로 저작권 보호 대상 아님. 프롬프트만으로 얻은 결과물을 그대로 쓰면 저작권 인정이 어렵고, 사람이 직접 수정·편집하거나 창작적으로 구성을 더하면 그 부분만 보호받을 수 있음.
- **2026년 3분기까지** AI 기업-창작자 상생 생태계를 반영한 저작권법 개정안이 국회 제출 예정(진행 중, 확정 여부는 **미확인**).

### 5-3. AI기본법 표시의무 (2026.1.1 시행, 핵심 — 클라이언트 납품 시 직접 관련)
AI기본법 제31조 투명성 확보 의무는 3단계:
1. **사전 고지 의무(제1항)**: 고영향 AI 또는 생성형 AI 기반으로 운용된다는 사실을 사전에 알려야 함 — 이용약관/계약서 명시, 소프트웨어·앱 구동 화면 고지, 오프라인 서비스는 이용자가 쉽게 볼 수 있는 장소에 안내문 게시.
2. **AI 생성물 표시 의무(제2항)**: 생성형 AI로 만들어졌다는 사실 표시. 서비스 환경 내부에서만 쓰이면 UI/로고 표시로 가능하고, 외부로 반출되는 경우 가시적 워터마크뿐 아니라 기계 인식용 비가시적 워터마크도 허용.
3. **딥페이크 고지·표시(제3항)**: 별도 강화된 의무.
4. **면제 사유**: AI 활용 사실이 명백한 경우, 또는 사업자 내부 업무용으로만 쓰이는 경우 등은 고지/표시 의무 전부 또는 일부 면제.

→ **실무 시사점**: 클라이언트에게 3D 포탈 갤러리/분기형 영화 등을 납품할 때 AI로 생성한 이미지·영상·3D 에셋이 최종 산출물에 포함된다면, 관리자 페이지나 사이트 UI 어딘가에 "이 콘텐츠 중 일부는 생성형 AI로 제작되었습니다" 류의 표시를 넣는 것이 2026년 기준 법적 의무일 가능성이 높음. 정확한 적용 범위(모든 산출물 vs 딥페이크성 콘텐츠만)는 **법률 자문으로 재확인 필요**.

### 5-4. 유명 IP 오마주/패러디 리스크
- 국내 사례: 인디게임 "마리오로얄"이 슈퍼마리오의 캐릭터·몬스터·아이템을 형태와 효과까지 그대로 재현했다가 닌텐도로부터 DMCA 위반 통보를 받고 이미지를 교체한 실제 사례 존재.
- 패러디/오마주는 국가별로 법적 취급이 다름 — 프랑스는 저작권법에 패러디를 제한적으로 허용한다고 명시하지만, 한국은 이런 명문 규정이 없어 공정이용 해당 여부를 사안별로 판단해야 함.
- 일반 대중은 저작권/상표권/특허권을 구분하지 않고 혼용하는 경우가 많지만, **상업적 이용 시에는 상표권 침해 위험이 특히 높다**는 점이 법률 콘텐츠에서 강조됨 — "오마주니까 괜찮다"는 인식과 실제 법적 위험 사이의 간극이 크다는 뜻.
→ 클라이언트 프로젝트에서 유명 IP(게임 캐릭터, 브랜드 로고 스타일 등)를 "오마주"로 차용하는 것은 특히 상업적 맥락에서 고위험. AI로 생성했다고 해도 결과물이 원작과 유사하면 동일한 침해 책임 구조 적용됨.

| PostHog | 제품 분석 올인원(퍼널, 세션 리플레이, 피처플래그, A/B테스트, 서베이, 에러 트래킹) | "유저가 왜 그렇게 행동하는가"에 특화 — 퍼널을 따라 세션을 리플레이하고 특정 지점에서 피처를 플래그로 제어 가능. 분기형 선택 이벤트 트래킹에 가장 적합해 보임(커스텀 이벤트 자유도 높음) |

→ **분기형 AI 영화/월드게임처럼 "노드별 선택률"을 봐야 하는 경우 PostHog가 커스텀 이벤트+퍼널+세션 리플레이 조합으로 가장 적합**. 단순 브랜드 소개 사이트(체류시간·방문경로 정도)만 필요하면 Plausible/Umami로 충분하고 비용도 훨씬 낮음.

### 6-2. 이벤트 트래킹 설계(분기 노드별 선택률)
- 업계 일반 패턴(인터랙티브 비디오 툴 Cinema8/Mindstamp 기준): **path completion rate(경로 완주율), cross-path rewatch rate(경로 간 재시청률), decision point drop-off(선택 지점 이탈률)**이 핵심 신호로 꼽힘.
- 분기형 콘텐츠는 "각 선택지에서 어떤 갈래를 택했는지, 어디서 이탈했는지, 어떤 엔딩까지 도달했는지"를 노드 단위 커스텀 이벤트로 남기고, 노드 ID를 속성으로 붙여 히트맵/퍼널 형태로 집계하는 것이 표준 설계로 보임.

### 6-3. 카메라 권한 허용률 등 지표
- 웹캠/카메라 권한 허용률에 대한 업계 평균치·벤치마크 데이터는 이번 조사에서 찾지 못함 **(미확인)**. 브라우저별 권한 요청 UX(Chrome/Firefox/Safari)에 대한 가이드는 존재하나 정량적 opt-in rate 통계는 확보하지 못함 — 직접 자체 사이트에서 계측해 벤치마크를 쌓는 것이 현실적.

### 6-4. 세션 리플레이 프라이버시
- GDPR 하에서 세션 리플레이는 단순 쿠키 배너로는 부족하고 **명시적 동의**가 필요할 수 있음(리플레이가 GDPR Article 22의 프로파일링에 해당할 정도로 상세하다는 해석 때문). 비밀번호·결제정보 등 민감 필드는 기본 마스킹 또는 완전 제외 설정 필요. 세션 리플레이 툴 제공사와는 GDPR Article 28에 따른 DPA(데이터처리계약) 체결이 필요. 히트맵은 집계 데이터라 리스크가 상대적으로 낮음(개인 단위가 아닌 수천 명 합산).
- → 한국 클라이언트 대상이라도 EU 방문자가 섞이면 GDPR 적용 가능성이 있으므로, 세션 리플레이를 켤 경우 쿠키 배너에 "세션 녹화" 항목을 명시적으로 분리해 동의받는 것이 안전.

## 7. 양산 조직 사례 — 반복 제작을 툴화한 업계

### 7-1. Playable Ads 업계 (직접적으로 참고할 가치 높음)
- **Playturbo**(Mintegral/Mobvista): 노코드 드래그앤드롭 에디터, **300개 이상의 템플릿**, AI 더빙, 100개 이상 언어 로컬라이제이션을 갖춘 "Creative Automation" 플랫폼. 광고주가 배경 이미지, CTA 버튼, 스킨, 음악/효과음, 난이도 같은 요소를 편집하면 즉시 새 버전의 플레이어블 광고를 자동 생성.
- **Luna Labs**: Unity 기반 엔드투엔드 크리에이티브 관리 플랫폼(Unity Playworks) — 게임 스튜디오가 플레이어블/비디오 광고를 무제한 반복(iterate) 생성·관리·최적화하도록 지원, 모든 주요 광고 네트워크로 내보내기(export) 가능.
- **시사점**: 이 두 사례는 정확히 "베이스를 만들고 설정값만 바꿔 대량 생성 + 다양한 네트워크/포맷으로 export"하는 구조 — 본 프로젝트의 "모노레포 + 템플릿 제너레이터"와 철학적으로 동일. 다만 이들은 (b)/(d) 혼합형(멀티테넌트 SaaS형 에디터)에 가깝다는 점이 주목할 만함 — 즉 업계가 이미 "많은 수의 변형을 낮은 한계비용으로 찍어내야 하는 문제"에서는 clone-per-project보다 파라미터화된 단일 엔진 쪽으로 수렴했다는 신호.

### 7-2. 1인/소규모 스튜디오의 템플릿 기반 다중 프로젝트 운영 공개 사례
- Indie Hackers 커뮤니티에 다수의 1인 창업자가 "AI로 만든 SaaS 포트폴리오"를 운영하는 사례들이 존재(예: $28K/월 SaaS 포트폴리오 사례, 10K MRR 케이스 스터디 등)하나, "인터랙티브 웹 템플릿 양산"에 정확히 일치하는 공개 사례·인터뷰는 이번 조사에서 찾지 못함 **(미확인)**. 강연자(김그륜)의 8개 동시 운영 사례 자체가 이 분야에서 상대적으로 희귀한 1차 사례로 보이며, 유사 규모의 공개된 타 사례는 확보하지 못함.
- Framer/Webflow 생태계에는 "패시브 인컴으로 템플릿을 만들어 판다"는 개인 크리에이터들의 사례가 다수 존재(Segment UI, Framespark 등 블로그)하지만 이들은 "직접 클라이언트 프로젝트를 양산"하기보다 "템플릿 자체를 상품화해서 마켓에 파는" 모델이라 본 프로젝트와는 사업모델이 다름 — 참고는 되지만 동일 사례는 아님.

|---|---|---|---|---|---|

| (c) 헤드리스 CMS + 템플릿 프론트 | 프론트 공유로 코드 유지보수는 절감, 콘텐츠 스키마 관리 비용 발생 | 프론트 코드 배포로 전파, CMS 스키마 버전 관리 별도 필요 | 콘텐츠 편집이 잦은 브랜드 플랫폼류에 최적 | 콘텐츠 구조는 스키마 내에서 제한, 비주얼은 프론트 자유도만큼 | 콘텐츠는 CMS(클라이언트 접근), 코드는 별도 |
| (d) 플랫폼화(SaaS) | 플랫폼 운영사가 전담(제작자는 매출만 관리) | 플랫폼 자체 업데이트로 자동 전파 | 수천 개 이상 (장기 옵션) | 사용자가 직접 편집(에디터 범위 내) | 완전 분리, 플랫폼이 전체 관리 |

**권고**: 현재 규모(모노레포 + 장르별 템플릿 제너레이터)에는 **(a)+(c) 하이브리드**가 가장 현실적 — 코어는 changesets로 semver 관리되는 공유 패키지, 관리자/콘텐츠 레이어는 헤드리스 CMS(Notion 미러링 포함) 패턴을 차용하고, 프로젝트별로 패키지 버전을 고정해 clone하는 구조.

## 법적 체크리스트

1. **AI 생성물 표시**: 최종 산출물에 AI로 생성된 이미지/영상/3D 에셋이 포함되면, AI기본법 제31조에 따라 UI/로고 또는 워터마크(가시/비가시)로 "생성형 AI 활용 사실"을 표시해야 할 가능성이 높음(2026.1.1 시행 중) — 서비스 화면 내 고지 문구, 딥페이크성 콘텐츠는 추가 강화 의무. 면제 사유(활용 사실이 명백하거나 내부 업무용)에 해당하는지 사안별 검토 필요.
2. **AI 도구 상업 라이선스 확인**: 사용하는 생성 AI 도구(Midjourney/Runway 등)가 (a) 팀/기업 매출 기준에 따라 상위 플랜 구매를 요구하는지, (b) 제3자 침해 클레임에 대한 면책을 제공하는지(대부분 소비자 플랜은 면책 없음 — 침해 리스크를 제작자가 직접 부담) 프로젝트 착수 전 확인.
3. **유명 IP 오마주 금지/주의**: "오마주"라는 표현이 법적 방패가 되지 않음 — 캐릭터·아이템·룩앤필을 형태·효과까지 재현하면 저작권(및 특히 상표권) 침해로 이어질 수 있음(마리오로얄 DMCA 통보 실제 사례). 클라이언트가 특정 IP 스타일을 요청해도 계약서에 "IP 유사성에 대한 법적 책임은 클라이언트 승인 후에도 제작사가 최종 검수한다"는 안전장치를 두는 것이 바람직.
4. **템플릿 재사용 IP 카브아웃**: 모든 클라이언트 계약서에 "베이스 템플릿/엔진/컴포넌트 라이브러리는 제작사 소유이며 클라이언트는 최종 커스터마이징 결과물에 대해서만 라이선스를 취득한다"는 명시적 제외 조항을 넣어야 함 — 없으면 work-for-hire 조항이 템플릿 자체까지 클라이언트 소유로 끌고 갈 위험. 해외 클라이언트는 미국식 work-for-hire가 자동 적용되지 않으므로 별도 IP 양도 조항 필요.
5. **세션 리플레이/카메라 권한 관련 동의**: 세션 리플레이(사용자 행동 상세 기록)는 GDPR 하에서 단순 쿠키 배너로는 부족하고 별도 명시적 동의가 필요할 수 있음 — EU 방문자 가능성이 있으면 동의 항목을 분리. 카메라 등 민감 권한 요청 시에도 "왜 필요한지"를 사전에 고지하는 것이 전환율과 법적 리스크 양쪽에 유리.
