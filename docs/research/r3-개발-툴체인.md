## 1. 바이브 코딩 도구 2026-09 현황 비교

### 1-1. Replit Agent
- 2026년 3월 11일 **Agent 4** 출시. 핵심 변화는 **멀티 아티팩트(multi-artifact) 지원**: 하나의 프로젝트(Repl)가 웹앱·모바일앱·피치덱 등 여러 산출물을 동시에 담을 수 있고, 이들이 **같은 DB·백엔드·시크릿·배포**를 공유한다. 즉 "관리자 탭 + 여러 프런트엔드"를 한 Repl 안에 두는 구조가 공식적으로 지원되기 시작했다.
  - 단, 2026-03-11 이전에 만든 프로젝트는 **단일 앱 레이아웃**이라 Agent가 1회성 구조 업그레이드를 해야 두 번째 아티팩트를 추가할 수 있다.
- Plan 모드(작업 목록을 순서대로 스케치), **Parallel Agents**(작업을 서브태스크로 나눠 병렬 처리) 지원.
- **모바일 앱(iOS/Android) 자체를 만드는 기능**: Expo 기반으로 실제 네이티브 코드를 생성하고, QR코드로 실기기 프리뷰. 카메라·위치 등 네이티브 API 접근 가능. 앱스토어 제출까지 가이드하지만 Apple Developer 계정은 사용자가 직접 준비해야 함.
- **Replit 모바일 앱(iOS/Android 클라이언트)**: 폰에서 Agent로 웹앱을 "바이브 코딩"할 수 있음. 단, 네이티브 iOS/Android 앱을 만드는 작업 자체는 웹에서 하라고 권장(모바일 클라이언트는 짧은 수정·확인용이며 장시간 코딩엔 부적합하다는 리뷰 다수).
- 가격(2026-09 기준): Starter 무료(제한적 Agent, 앱 1개 퍼블리시), **Core $20/월(연간 결제, $25/월 다는 표기도 있음)** + 월 $20~25 사용 크레딧, **Pro $100/월**(빌더 15명까지 플랫 요금, 2026-02-20 출시, 기존 Teams 플랜 대체), Enterprise 커스텀. 2025년 중반부터 **"effort-based pricing"**(작업 난이도에 따라 크레딧 소모 가변)로 전환.
- 배포: Autoscale(기본료 $2/월 + 컴퓨트 단위당 $0.60/백만 + 요청 $0.40/백만), Reserved VM $15(0.5vCPU/2GB, shared)~$130(4vCPU/16GB) /월. 커스텀 도메인·HTTPS는 Core 이상, 프라이빗 배포·리전 선택·PostgreSQL 호스팅은 Pro 필요.
- 2026-09-04 체인지로그: 프로덕션 DB용 **예약 백업(daily restore point)**, **Project Analytics**(방문자·페이지·트래픽소스·국가·브라우저 통계, 유료 플랜은 Agent에게 커스텀 이벤트/퍼널 분석 요청 가능) 추가.

### 1-2. Claude Code
- 확장 레이어가 명확히 분리됨: **메모리(CLAUDE.md) / 훅(Hooks) / 스킬(Skills) / 서브에이전트(Subagents) / 플러그인(Plugins) / MCP**.
  - 슬래시 커맨드=프롬프트 템플릿, 스킬=실제 도메인 로직+헬퍼 파일이 있을 때, 서브에이전트=격리된 컨텍스트에서 병렬 작업, 훅=결정론적으로 규칙을 강제할 때.
- **훅(Hooks)**: PreToolUse, SessionStart, SubagentStop 등 라이프사이클 이벤트에서 셸 스크립트를 실행해 위험한 작업 차단, 컨텍스트 주입, 로깅, 보안 정책 강제 가능. CLAUDE.md의 지시는 "약 70% 정도만 지켜진다"는 평가가 있어, 100% 강제해야 하는 규칙(린트 실행, 커밋 전 검사 등)은 훅으로 백업해야 한다는 것이 커뮤니티 컨센서스.
- **git worktree 지원**: Claude Code v2.1.49(2026-02)에서 정식 지원. `-w` 플래그로 같은 저장소에 대해 브랜치별로 격리된 워크트리를 만들어 여러 Claude 세션을 동시에 돌릴 수 있음(파일은 격리되지만 DB·env·실행 중인 서비스는 격리되지 않음에 주의). 실무에서는 개발자 1인당 동시 2~8개 워크트리를 굴리는 사례가 보고됨(리뷰가 병목이 되는 경우가 많음).
- **플러그인 마켓플레이스**: `anthropics/claude-plugins-official` 공식 저장소가 존재. 플러그인은 `.claude-plugin/plugin.json`(필수) + 선택적으로 MCP 서버 설정, 슬래시 커맨드, 에이전트 정의, 스킬 정의를 포함하는 구성. Skills+Subagents+Hooks+MCP+LSP를 한 번에 설치하는 "composable extension system"을 제공.
- **비대화형/헤드리스 모드(`claude -p`)**: 프롬프트 1개→결과 1개→종료. `--output-format`, `--max-turns`, `--model`, `--allowedTools`와 조합해 CI에서 파싱 가능한 결과를 얻음. 공식 GitHub Action `anthropics/claude-code-action@v1`이 헤드리스 실행을 GitHub 플러밍(이슈/PR 코멘트 등)과 연결. CI에서는 `--dangerously-skip-permissions`와 함께 쓰는 패턴이 일반적. 종료 코드 0/비0으로 성공·실패 판정 가능.
- 3D/비디오 코드: 공식 기능은 아니지만, Three.js/GLSL/파티클시스템/GPU 렌더 디버깅을 다루는 커뮤니티 스킬(`webgl-animation-skills` 등)이 존재. 리뷰에 따르면 Claude Code는 아키텍처 결정력이 좋고(생성 코드가 정리할 게 적음), 대신 MVP 도달 속도는 Replit Agent보다 느림.

## 2. "복제 → 확장" 자동화 비교

- **Turborepo generators (`turbo gen`)**: Plop.js 기반. 템플릿에서 파일을 스캐폴딩하고 커스텀 액션 함수로 프로그래매틱 스텝 지원. **AST 레벨 코드 수정, 프로젝트 그래프 인식, 마이그레이션/코드모드 시스템은 없음.** 5~50개 패키지 규모의 JS/TS 모노레포에 적합.
- **Nx generators**: Nx Devkit 기반의 완전한 프로그래매틱 API. 프로젝트 그래프를 읽고 수정, AST 레벨 TypeScript 변환, 다른 제너레이터와 조합 가능. 팀 고유 패턴을 인코딩한 로컬 워크스페이스 제너레이터 작성 가능. 대규모/멀티팀/폴리글랏 코드베이스, 거버넌스+코드 생성이 필요할 때 적합.
- **Plop / Hygen**: 외부 도구로, Turborepo/Moon 태스크에 통합해서 쓰는 방식. 별도 설치·유지보수 필요하지만 Turborepo 사용자들이 실제로 이 조합을 가장 많이 씀.
- **degit**: git 히스토리 없이 저장소를 복사하는 초경량 스캐폴딩 툴(Rich Harris 작). `degit.json`으로 post-clone 액션 구성 가능, 서브디렉토리/파일 필터/별칭 지원, tar 아카이브 캐싱으로 오프라인 재사용 가능. giget/tiged가 후속 대안으로 언급됨.
- **GitHub Template Repository**: 브라우저에서 바로 "Use this template" 버튼으로 새 저장소 생성. 로컬 설치 불필요.
- **Cookiecutter류**: `cookiecutter.json` + Jinja2 템플릿 디렉토리로 1회성 스캐폴딩에 최적화. 단, 업스트림 템플릿 변경을 기존 프로젝트에 병합하는 기능은 없음 → 그 문제를 해결한 것이 **Copier**(cookiecutter의 진화형, 템플릿 업데이트 동기화 지원).
- **`pnpm new <family> <name>` 제너레이터 모범 사례(리서치 기반 정리, 공식 pnpm 네이티브 명령은 아님)**:
  1. `apps/`(독립 실행 앱, 다른 패키지가 import하지 않음) vs `packages/`(재사용 가능한 라이브러리) 구조 분리.
  2. 새 앱 추가 = `apps/` 안의 샘플 앱을 복제 → 이름 변경 → `package.json`의 `name` 필드 갱신, 이 흐름을 Turborepo `turbo gen`(Plop 기반) 또는 Nx generator로 스크립트화.
  3. 루트 `package.json`에 `packageManager`로 pnpm 버전 고정.
  4. 실제 네이티브 `pnpm new` 명령은 확인되지 않음 — 커스텀 CLI(`tools/new-app`)를 Plop/Hygen/degit 조합으로 직접 구현하는 것이 현재 생태계의 표준 접근.

### 권장: `interactive-web` 리포용 선택
- 규모(3~4개 패밀리, 앱 1개=Repl 1개 대응)를 고려하면 **Nx의 풀파워는 과함**. **Turborepo + `turbo gen`(Plop 기반) + 필요시 degit으로 외부 템플릿 pull**을 `tools/new-app`에 얹는 조합이 실용적. Copier는 "템플릿이 계속 갱신되고 기존 앱에도 반영해야 하는" 요구가 생기면 고려.

## 3. Claude Code로 "앱 공장"을 만드는 패턴

- **레이어 선택 기준**(다수 소스 일치):
  - 슬래시 커맨드 = 단순 프롬프트 템플릿
  - **스킬(SKILL.md)** = 실제 도메인 로직 + 헬퍼 스크립트/에셋이 있는 경우 → "패밀리별 제작 절차"(예: 3D 쇼케이스 패밀리, 비디오 인터랙티브 패밀리)를 캡슐화하기에 정확히 맞는 단위
  - **서브에이전트** = 격리된 컨텍스트에서 병렬 실행이 필요한 작업(에셋 파이프라인, QA, 코드리뷰 등)
  - **훅** = 100% 강제해야 하는 규칙(성능 예산 체크, 린트, 커밋 전 검사)
- 스킬 디렉토리 구조 예: `.claude/skills/<family>/SKILL.md` + 서포팅 스크립트. Claude Code는 세션마다 폴더명+description을 읽고, 현재 태스크가 매치되면 본문을 로드.
- **Obra의 Superpowers 컬렉션**(이 세션에서도 스킬로 설치되어 있음: `superpowers:*`)이 실제 "소프트웨어 팩토리" 패턴의 참조 사례로 언급됨: brainstorming → git worktree 준비 → implementation planning → subagent-driven execution → TDD → 코드 리뷰 후 merge까지 체인으로 연결. 이 리포에도 이미 `writing-plans`, `subagent-driven-development`, `using-git-worktrees`, `test-driven-development`, `finishing-a-development-branch` 스킬이 들어와 있어 그대로 "패밀리별 신규 앱 생성" 파이프라인의 뼈대로 재사용 가능.
- **병렬 QA 패턴 예시**: "REST 컨벤션에 따라 API 엔드포인트 업데이트"용 서브에이전트 + "testing-conventions 스킬을 따라 통합 테스트 업데이트"용 서브에이전트를 동시에 디스패치하는 식으로 독립적인 QA 작업을 병렬화.
- **비대화형 배치(`claude -p`) + GitHub Actions**: `anthropics/claude-code-action@v1`을 사용해 PR 생성/이슈 트리아지/성능 예산 체크 등을 CI에서 자동 실행하는 것이 표준 패턴. `--output-format json`으로 결과를 파싱해 다음 스텝(예: PR 코멘트, Slack 알림)에 연결.
- **적용 제안**: `tools/new-app` 제너레이터가 뼈대(디렉토리, package.json, 관리자 스캐폴드)를 만든 뒤, Claude Code 스킬(`family-<name>-build`)이 "설정 스키마 작성 → 폼 자동생성 → 렌더링 → 훅으로 성능예산 체크 → 서브에이전트로 QA" 순서를 강제하는 이중 구조가 합리적.

## 4. 관리자 우선 개발을 위한 프롬프트/스펙 패턴

- **핵심 원칙**: "CLAUDE.md는 컨텍스트일 뿐 샌드박스가 아니다." CLAUDE.md의 규칙은 모델이 참고하지만 강제되지 않으며(약 70% 준수율이라는 커뮤니티 추정치), **실제 강제는 린트 규칙 + 훅으로 뒷받침**해야 한다는 것이 명확한 컨센서스.
  - 예: "Zod로만 검증할 것"을 CLAUDE.md에 적어도 다른 라이브러리를 쓸 수 있음 → 더 강한 제약(훅에서 `zod` import 여부를 grep해서 실패시키는 PreToolUse/PostToolUse 훅, 또는 ESLint import-boundary 플러그인)이 필요.
- **스키마 주도 UI 생성 실제 사례**:
  - **AutoForm**(`vantezzen/autoform`): 기존 데이터 스키마(Zod/Yup/Joi)로부터 자동으로 폼을 렌더링. shadcn/ui, Material UI, Mantine, Ant Design, Chakra UI 공식 패키지 제공. **Cursor/Claude Code/GitHub Copilot용 스킬을 자체 제공**해서 AI 코딩 에이전트가 AutoForm 컨벤션을 따르게 함 — "설정 스키마 먼저 → 폼 자동생성" 규율을 도구 레벨에서 강제하는 좋은 참조 사례.
  - **SmartForm(A2UI)**: 폼을 스키마로 정의하고 AI 에이전트가 MCP로 프로그래매틱하게 채우는 프로토콜. "정의 한 번, 어디서나 배포"라는 슬로건.
- **린트/스냅샷 테스트로 강제하는 구체적 방법(리서치 기반 권장, 리포 특화 미확인)**:
  1. 관리자에서 조작 가능해야 할 "설정 스키마"를 Zod 스키마로 `packages/schemas/<family>.ts`에 단일 소스로 둔다.
  2. `json-schema-to-zod` 류로 JSON Schema ↔ Zod 상호 변환, 타입 자동 생성.
  3. 스키마 변경 시 스냅샷 테스트(Vitest snapshot)로 "필드가 빠짐없이 관리자 폼에 매핑되는지" 검증.
  4. PreToolUse 훅으로 "새 기능 코드에 대응하는 관리자 폼 필드가 없으면 커밋 차단"하는 식의 정책을 셸 스크립트로 구현 — 이것이 사용자가 원하는 "네가 만드는 모든 기능은 관리자 탭에서 조작 가능하게" 조건을 코드 레벨에서 강제하는 방법.
- (미확인): AutoForm/SmartForm 외에 "관리자 우선"을 정면으로 표방하는 상용 템플릿·오픈소스 보일러플레이트가 있는지는 추가 조사 필요.

## 7. QA 자동화

- **Playwright + 3D(WebGL/Canvas)**: 네이티브 브라우저 이벤트를 쓰므로 캔버스 렌더링 테스트에 적합. Chromium 헤드리스 신모드(Playwright v1.49+)에서 하드웨어 가속 사용 시 별도 플래그 필요, Firefox는 기본 가속 활성(단 Xvfb에서만), **WebKit은 헤드리스에서 하드웨어 가속 미지원 → headed로 실행해야 함**.
- **카메라/마이크 모킹**: Chromium 실행 옵션 `--use-fake-ui-for-media-stream`, `--use-fake-device-for-media-stream`을 `playwright.config`의 launch options에 추가. Firefox는 `firefoxUserPrefs`에 `"media.navigator.streams.fake": true`, `"media.navigator.permission.disabled": true` 설정. 권한 팝업을 억제하지 않고 명시적으로 승인하려면 `context.grant_permissions(["microphone", "camera"])`를 `--use-fake-device-for-media-stream`과 함께 사용.
- **성능 예산 CI**:
  - **Lighthouse CI(`@lhci/cli`)**: `lighthouserc.js`에 assertion(예: performance score ≥ 0.9) 또는 `budget.json`(예: 스크립트 총량 ≤ 300KB) 정의 → GitHub Actions에 연결 → autorun이 URL당 3회 감사, 중앙값을 assertion과 비교, 위반 시 non-zero exit. 2026년 현재 Lighthouse 12.6.1 사용(PWA 카테고리는 12에서 제거됨, Lighthouse 13은 Node 22.19+ 필요해 아직 LHCI 미지원).
  - **size-limit**: `package.json`에 경로별 용량/실행시간 한도 정의(예: `{"path":"dist/index.js","limit":"4500 ms"}`) → `andresz1/size-limit-action`으로 GitHub Actions에 연결, PR에 번들 크기 변화를 코멘트로 자동 게시. 바이트 수보다 "다운로드+파싱+실행 시간"을 지표로 쓰는 게 더 정확하다는 점을 강조.
- **시각 회귀**:
  - **Chromatic**(Storybook 팀 제작, Storybook 통합 최고, Playwright/Cypress도 지원): $179/월~(3.5만 스냅샷), 초과 시 스냅샷당 $0.008.
  - **Percy**: 2026-07 기준 가격 페이지가 404로, 공개 가격 미제공(구버전 정보로 $599/월~ 언급됨). 무료 티어 월 5,000 스냅샷(Chromatic과 동일).
  - **Argos CI**: 무료 5,000 스냅샷/월, 이후 $100/월 플랫 — 예산 제약이 있다면 가장 저렴한 대안.
  - Playwright 자체의 `toHaveScreenshot()`은 무료지만 팀 리뷰 워크플로우가 없음.

**권장**: 이 프로젝트는 3D/비디오/카메라 인터랙션이 핵심이므로 (1) Playwright에 fake-device 플래그로 카메라 시나리오 커버, (2) WebKit 비중이 낮다면 Chromium+headed 조합으로 WebGL 렌더 확인, (3) size-limit + Lighthouse CI를 GitHub Actions에 넣어 패밀리별 성능 예산을 강제, (4) 시각 회귀는 초기엔 Playwright 내장 스크린샷 비교로 시작하고, 팀 규모가 커지면 Argos(저비용) 또는 Chromatic(Storybook 병행 시)로 이관.

## 8. 병렬 프로젝트 운용 워크플로우

- **git worktree 패턴**: Claude Code v2.1.49(2026-02)부터 `-w` 플래그로 정식 지원. 같은 저장소에서 브랜치별로 완전히 격리된 워킹 디렉토리+Claude 컨텍스트를 만들어 "컨텍스트 오염 없이" 여러 작업을 동시 진행. 단 DB/env/실행 중 서비스는 공유되므로 마이그레이션 등 상태 변경 작업이 겹치면 충돌 위험.
- **현실적 상한**: 이론적으로는 4~8개 워크트리를 동시에 굴리는 사례가 보고되지만, 병목은 대개 "Claude의 처리 속도"가 아니라 "사람의 리뷰 대역폭". 2~3개가 지속 가능한 상한이라는 의견과 4~8개가 실무 상한이라는 의견이 공존 — 팀/개인 리뷰 역량에 달림.
- 이 세션에도 이미 **`superpowers:using-git-worktrees`**, **`superpowers:dispatching-parallel-agents`** 스킬이 설치돼 있어, "3~4개 프로젝트 병렬" 요구사항과 직접 맞아떨어짐. 실무 팁: 각 워크트리(=각 앱 패밀리)마다 별도 `.env`/로컬 DB 포트를 할당해 충돌을 원천 차단.
- 이슈 기반 작업 분리(각 앱=각 GitHub 이슈/브랜치)와 워크트리를 짝지으면, "Repl 복제" 방식과 유사한 감각으로 모노레포 내에서도 병렬 확장이 가능.
- (미확인): Replit 모바일에서의 "클라우드 병렬 작업" 구체 사례(여러 Repl을 폰에서 동시에 굴리는 워크플로우)는 이번 조사에서 구체적 사례를 찾지 못함.

## Replit vs Claude Code 역할 분담 권고

- **Replit**: (1) 신규 패밀리의 "0→1 초안"을 강연자 방식대로 Agent로 빠르게 뽑아낼 때, (2) 비개발자/외주 협업자가 관리자에서 눈으로 보며 확인·수정할 때, (3) 폰에서 급한 텍스트/카피/설정 수정을 할 때, (4) 데모용 Autoscale 배포처럼 "완결된 독립 인스턴스"가 필요할 때 — 즉 **개별 의뢰(고객사) 단위의 독립 Repl 운영**에 최적.
- **Claude Code**: (1) 모노레포(`apps/`+`packages/`+`templates/`+`tools/new-app`) 구조 자체를 설계·유지할 때, (2) 패밀리별 제작 절차를 스킬로 캡슐화하고 훅으로 "관리자 노출 규율"을 강제할 때, (3) 3~4개 프로젝트를 worktree로 동시에 진행하며 서브에이전트로 QA/에셋 파이프라인을 병렬화할 때, (4) GitHub Actions + `claude -p`로 성능예산·린트·회귀 테스트를 CI에 자동화할 때 — 즉 **툴 자체(제너레이터, 공통 패키지, CI, QA)를 만들고 지키는 엔지니어링 축**에 최적.
- **권장 분업 구도**: Replit = "의뢰별 최종 산출물이 사는 곳(또는 빠른 초안 실험실)", Claude Code+모노레포 = "그 산출물을 찍어내는 공장(제너레이터+스킬+CI)". 장기적으로 관리자·에셋 업로드·분기 편집까지 자체 코드로 완성되면("바이브 코딩 없이 다음 작품") Replit 의존도는 초안 단계로 축소되고, 실제 양산은 Claude Code 기반 모노레포 파이프라인이 담당하는 방향이 목표에 부합.
