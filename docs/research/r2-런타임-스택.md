## 1. 3D 런타임

### 현재 최선
- **three.js**: r180 전후 버전이 2026년 초 기준 최신으로 언급됨(정확한 r-번호는 소스마다 r180/r184/r186으로 엇갈려 **미확인** — 공식 GitHub releases 페이지를 직접 확인 필요). WebGPU 렌더러는 계속 성숙 중: r180에서 TSL(Three Shading Language)에 주석 지원 추가, WebGPU 텍스처 포맷(ASTC, BC4/BC5, RGB9E5 등) 확장, WebGPU 카메라가 WebGL 데모와 정렬됨. TSL은 WebGL2와 WebGPU 양쪽에서 동작하는 통합 셰이더 언어로 자리잡는 중. 라이선스: MIT.
- **React Three Fiber (R3F) v9**: 안정 버전은 9.7.0대(2026년 중반 기준, "한 달 전 게시"로 표기된 스냅샷 존재 — 정확 날짜 **미확인**). React 19.0~19.2 전 범위 호환. v10은 2026-01-17 alpha.1부터 알파 진행 중이며 아직 프로덕션 비권장. **drei**는 R3F v9/React 19 호환성 논의가 활발하며 대체로 따라감. 라이선스: MIT.
- **Threlte (Svelte)**: @threlte/core, extras, gltf, rapier(물리), theatre(Theatre.js 연동), xr, flex 패키지로 구성된 선언적 Svelte 3D 프레임워크. Rapier 물리·Theatre.js 애니메이션이 기본 통합되어 있는 점이 특징. 정확한 2026 버전 번호는 **미확인**.
- **PlayCanvas Engine**: MIT 라이선스, GitHub `playcanvas/engine`, 2011-2026 저작권 표기로 2026년에도 활발히 개발 중. WebGL+WebGPU+WebXR+glTF 지원. 엔진 자체는 150KB 미만으로 가볍고, 모바일 프레임레이트에서 다른 엔진보다 우수하다는 평가가 다수 소스에서 반복됨. 클라우드 기반 비주얼 에디터(디자이너 협업)가 강점.
- **Needle Engine**: Unity/Blender 등에서 만든 씬을 웹으로 내보내는 워크플로우 특화 엔진(three.js 기반). 가격/라이선스 정보는 검색으로 **미확인**(공식 사이트 직접 확인 필요) — 상용 라이선스로 추정.
- **Babylon.js**: MS 백킹의 완전한 게임엔진급 라이브러리, 물리엔진 내장, 무료. 에디터 드리븐 워크플로우보다 코드 중심.

### 대안
- Threlte(스벨트 스택으로 완전 전환 시), PlayCanvas(에디터 협업이 중요할 때), Babylon.js(물리/XR 풀스택이 필요할 때), Needle Engine(DCC 툴 파이프라인 중심일 때).

### 판단
**채택**: three.js + R3F v9 + drei — 이미 스택 확정, 생태계(코드젠 도구·바이브 코딩 친화도 포함)가 가장 크고 pmndrs 생태계(zustand, drei, leva, zundo 등)와의 정합성이 높음. React 기반이라 우리 admin-form 자동생성 원칙과도 결이 맞음.
**보류**: WebGPU/TSL 전면 전환 — 아직 WebGL2 폴백이 필요한 브라우저(구형 모바일)가 남아있어, TSL로 셰이더를 작성하되 WebGPURenderer는 선택적 백엔드로만 관찰.
**관찰**: PlayCanvas(모바일 성능이 병목이 될 경우 대안으로), Needle Engine(디자이너가 Blender/Unity에서 씬을 직접 만드는 워크플로우가 필요해지면).

## 2. 가우시안 스플래팅 웹 뷰어

### 현재 최선
- **Spark (World Labs, sparkjsdev/spark)**: three.js 위에서 동작하는 고급 3DGS 렌더러. WebGL2 기반, 데스크톱/iOS/Android/VR 브라우저 지원. Spark 2.0(2026-04-15 릴리스)에서 스트리밍, LOD, GPU 가상 메모리 도입 — 1억 개 이상 스플랫을 브라우저에서 스트리밍 렌더링 가능. 멀티 3DGS 오브젝트를 한 씬에 배치, 실시간 편집/릴라이팅, 셰이더 그래프 지원. **`spark-react-r3f`** 공식 패키지로 R3F 안에 선언적으로(`<SparkRenderer>`, `<SplatMesh>`) 넣을 수 있음 — 우리 R3F 스택과 직접 통합 가능. 지원 포맷: .PLY, .SPZ, .SPLAT, .KSPLAT, .SOG. 라이선스: 오픈소스(정확한 라이선스 종류는 **미확인**, GitHub 리포 확인 필요).
- **PlayCanvas SuperSplat / splat-transform**: 브라우저 재생 엔진 중 가장 강력한 축에 속하는 오픈소스 에디터+뷰어. .ply/.compressed.ply/.splat/.ksplat/.spz/.sog(번들)/meta.json(언번들 SOG)/lod-meta.json(스트리밍 SOG) 전부 임포트 가능. `splat-transform` CLI로 포맷 변환.
- **gsplat.js / GaussianSplats3D(mkkellogg)**: KSplat 포맷 생태계의 사실상 표준 뷰어 라이브러리군. Spark 대비 커뮤니티 기반이 넓지만 기능 확장(편집, 셰이더 그래프)은 Spark가 앞섬.

### 포맷
- **.SPZ**: Niantic 주도 오픈 압축 포맷. ZSTD 압축 + 양자화로 PLY 대비 약 10배 작음, 시각적 손실 거의 없음. v4만 지원되는 경우가 많음.
- **.SOG**: PlayCanvas가 오픈소스화한 "웹의 WebP" 격 포맷. Compressed PLY 대비 2~3배 추가 압축. 스트리밍(LOD) 메타데이터 지원.
- **.PLY**: 원본/무손실이나 용량이 크다. 모바일 딜리버리용으로는 부적합.
- 2026 시점 포맷 지형: SPZ/SOG가 세력을 넓히는 중이며, KSplat은 GaussianSplats3D 계열 뷰어에서 여전히 지배적. 신규 프로젝트 기본 딜리버리 포맷은 SPZ 또는 SOG가 유력.

### 판단
**채택**: Spark(+spark-react-r3f) — three-kit 패키지의 GLB 로더 옆에 스플랫 로더로 자연스럽게 통합 가능하고, R3F 선언형 API가 우리 관리자 스키마 기반 씬 구성과 궁합이 좋음. 딜리버리 포맷은 SOG(스트리밍/LOD 필요 시) 또는 SPZ(단순 정적 씬)를 기본으로.
**관찰**: PlayCanvas splat-transform은 CLI 변환 도구로만 채택(빌드 파이프라인에서 PLY→SOG/SPZ 변환용), 뷰어 자체는 필요 없음.
**리스크**: 모바일(특히 iOS Safari) 성능은 스플랫 수·압축률에 크게 좌우되므로 대용량 씬은 LOD/스트리밍 필수.

## 3. 에디터 UI 계층

### 현재 최선
- **Leva**: React-first tweaking GUI, dat.gui/lil-gui의 사실상 후계. 주간 다운로드 약 56만(비교 대상 중 최고), R3F 생태계 표준으로 자리잡음. 관리자 슬라이더/디버그 패널에 적합.
- **Tweakpane**: 플러그인 생태계가 강점(컬러피커, 그래프 등), 프레임워크 비의존적. 주간 다운로드 약 21.7만.
- **dat.gui**: 2년 이상 미유지보수, 사실상 legacy. 신규 채택 비권장.
- **drei TransformControls / PivotControls**: R3F 씬 안에서 오브젝트를 기즈모로 직접 조작하는 표준 컴포넌트. three-kit의 기즈모 요구사항과 직접 매칭.
- **zundo**: zustand용 undo/redo 미들웨어, 700바이트 미만. 최신 버전 2.3.0(문서상 "2년 전 게시"로 표기 — 최근 커밋 활동은 **미확인**, GitHub 직접 확인 권장). Zustand v4.2+/v5 지원.
- **Triplex (pmndrs)**: R3F 컴포넌트용 비주얼 워크스페이스. 코드가 source of truth이며 TS props를 읽어 시각 편집 → 코드에 직접 반영하는 양방향 바인딩. VS Code 확장으로도 제공. "페이지 안 씬 에디터"를 직접 만들지 않고 개발자용 도구로 쓸 수 있음(단, 우리가 필요한 건 "런타임 관리자 UI"이므로 Triplex는 개발 단계 보조 도구에 가깝고 최종 산출물엔 포함되지 않음).
- **three.js editor(공식)**: 범용 씬 에디터, 우리 도메인 특화 요구(관리자 폼 자동생성)에는 직접 재사용하기 어려움 — 참고용.

### 대안
- dat.gui(비권장), react-three-editor류 커뮤니티 프로젝트(성숙도 낮음).

### 판단
**채택**: Leva(관리자 디버그 패널) + drei TransformControls/PivotControls(씬 기즈모) + zundo(히스토리, core-admin과 three-kit 양쪽에서 공유 가능). 이 조합이 "페이지 안 씬 에디터 + 관리자 슬라이더"를 가장 적은 커스텀 코드로 만족.
**관찰**: Triplex는 팀 내부 개발 생산성 도구로 참고(최종 제품에 임베드하지 않음).
**리스크**: zundo 유지보수 상태 미확인 — 채택 전 GitHub 커밋 이력 직접 재확인 필요, 활동 저조 시 자체 undo 스택(단순 zustand 미들웨어)으로 대체 가능.

## 4. 페이스/핸드 트래킹

### 현재 최선
- **MediaPipe Tasks (`@mediapipe/tasks-vision`)**: FaceLandmarker, HandLandmarker 모두 활발히 유지보수 중. 공식 문서 최종 업데이트 2026-08-17 확인. Google이 NPM 배포 보안(2FA 우회 토큰 제한, 2026-08 계획, 2027-01 직접 배포 전환)을 강화 중이나 패키지 자체의 지속 유지에는 영향 없어 보임. Web/JS 런타임 정식 지원.
- **오프-액시스 프로젝션**: three.js `PerspectiveCamera.setViewOffset()` + `makePerspective()`로 비대칭 절두체(frustum)를 매 프레임 갱신하는 방식이 표준 레퍼런스. MediaPipe FaceMesh/FaceLandmarker로 머리 위치 추적 → setViewOffset 매 프레임 호출 패턴의 데모(MindDock/off-axis-demo 등)가 참고 가능.
- **모바일 자이로 폴백**: 검색으로 구체적 레�퍼런스는 **미확인** — DeviceOrientation API 기반 폴백을 자체 구현 필요(업계 일반 패턴이나 공식 문서 링크는 못 찾음).

### 대안
- **TensorFlow.js + face-api.js**: face-api.js는 유지보수 상태가 불확실("사용 전 유지보수/보안 상태 확인" 권고), 신규 프로젝트에는 비권장. `modern-face-api`라는 커뮤니티 포크가 존재하나 성숙도 **미확인**.
- **Human 라이브러리**: 얼굴/포즈/손가락/홍채/나이·성별·감정/시선/제스처까지 통합한 올인원 라이브러리. MediaPipe보다 기능 범위는 넓으나 번들 크기·성능 트레이드오프 존재.

### 판단
**채택**: MediaPipe Tasks(FaceLandmarker/HandLandmarker) — 공식 지원, 활발한 유지보수, WASM/GPU 델리게이트로 모바일 성능 확보. off-axis 구현은 setViewOffset 패턴 직접 구현.
**보류**: Human/TF.js 대안 — 기능 과잉이거나(Human) 유지보수 리스크(face-api.js)가 있어 tracking 패키지의 기본값으로는 채택하지 않음. 특수 요구(홍채 분석, 감정 인식 등) 발생 시에만 관찰.
**리스크**: iOS Safari 카메라 권한/성능 편차, 자이로 폴백 미구현 상태.

## 5. 인터랙티브 비디오

### 현재 최선
- **기술 기법**: hls.js가 HLS 플레이리스트를 브라우저 MSE(Media Source Extensions) 위에 얹는 사실상 표준. stream controller, ABR controller, buffer controller, EME controller, LL-HLS 인식 로더로 구성. 분기 지점에서 끊김을 없애려면 (1) 다음 분기 클립을 프리로드, (2) 더블 버퍼링(두 개의 `<video>` 엘리먼트를 번갈아 노출/숨김 전환)하는 패턴이 업계 일반적 접근으로 언급됨 — 단, 구체적 오픈소스 레퍼런스 구현은 **미확인**.
- **영상 인프라**: **Mux** — 개발자 우선 API, 업로드→HLS ABR 스트림+썸네일+GIF 프리뷰+자막+초 단위 분석 자동 생성, SaaS 임베드에 최적화. **Cloudflare Stream** — Cloudflare 네트워크에 깊이 통합, 같은 CDN 경유, API 표면이 작고 단순. **Cloudflare R2**는 별도 오브젝트 스토리지(egress 비용 없음)로 원본 보관용.
- **상용 인터랙티브 비디오 툴 데이터 모델 참고**: **Eko** — 이커머스 특화, 분기형 "choose your own adventure" 내러티브 제작+웹 배포 겸용 툴. **Mindstamp** — 온보딩/트레이닝/세일즈용, 비디오 내용 기반 AI 어시스턴트 내장, 커스텀 경로/퀴즈/피드백. **Vimeo Interactive** — 퀴즈·분기 내러티브용 클릭형 경험.

### 대안
- Bunny Stream(비용 절감형 대안, 세부 **미확인**), 자체 S3+CloudFront+hls.js 파이프라인(가장 유연하지만 구현 부담 큼).

### 판단
**채택**: Mux(개발 초기, DX·분석 우선) 또는 Cloudflare Stream(이미 Cloudflare 생태계에 있거나 비용 민감 시) 중 택1 — video-kit 패키지 설계 시 둘 다 추상화 가능하도록 어댑터 패턴 권장. 분기 재생은 hls.js + 더블 버퍼 `<video>` 엘리먼트 자체 구현.
**참고(채택 아님)**: Eko/Mindstamp/Vimeo Interactive의 노드-분기 데이터 모델(JSON 트리 구조, 조건부 전환, 클릭형 핫스팟)을 flow-editor의 분기 스토리 스키마 설계 시 참고.
**리스크**: 분기 전환 끊김 방지(디코더 워밍업, 프리롤) 구현 난이도가 가장 큰 미지수 — PoC 필요.

## 6. 노드 캔버스

### 현재 최선
- **React Flow (@xyflow/react)**: 최신 버전 12.11.6("5일 전 게시"로 표기된 스냅샷, 절대 날짜는 **미확인**). MIT 라이선스. 2026-05 기준 GitHub 3만 6,400+ 스타. 각 노드가 일반 React 컴포넌트라 커스텀 노드(예: "AI 생성 호출" 버튼이 있는 노드) 구현이 매우 쉬움. 대규모 그래프(수천 노드)에서는 캔버스 렌더링 대비 성능 열세라는 트레이드오프가 명시됨. 구(舊) `reactflow` 패키지(v11.11.4)는 사실상 폐기, `@xyflow/react`로 이전 완료.

- **Rete.js**: 검색 결과에서 구체적 2026 정보 확보 실패(**미확인**) — 프레임워크 비의존적 노드 에디터로 알려져 있으나 이번 조사에서 최신 근거를 못 찾음.

**채택**: React Flow(@xyflow/react) — MIT 라이선스로 상용 제약 없음, 노드=React 컴포넌트라 "노드에서 AI 생성 호출" UI(버튼, 로딩 상태, 결과 미리보기)를 그대로 React로 구현 가능해 flow-editor 패키지의 기반으로 가장 적합. 우리 규모(분기 스토리 편집기, 수십~수백 노드)에서는 성능 문제도 크지 않을 것으로 판단.

## 7. 스키마→폼/관리자 자동 생성

### 현재 최선
- **zod의 내장 `z.toJSONSchema()`**: Zod 자체에 JSON Schema 변환 기능이 내장됨(Draft 2020-12 기본, draft-07/2020-12/draft-04/openapi-3.0 타겟 선택 가능). 별도 `zod-to-json-schema` 패키지 없이도 최신 Zod에서 가능 — 우리 config-schema 패키지의 "zod 스키마 하나로 폼+검증+문서" 원칙에 정확히 부합.
- **AutoForm (vantezzen/autoform, shadcn 통합)**: zod 스키마 기반으로 @shadcn/ui 폼을 자동 생성하는 React 컴포넌트. React Hook Form 기반, Material UI/Mantine/Ant Design/Chakra UI 등 다중 UI 라이브러리 공식 패키지 제공, Zod/Yup/Joi 검증 라이브러리 지원. "기존 zod 스키마로 내부용/저우선순위 관리자 폼을 빠르게 만드는" 용도로 명시적으로 추천됨 — 우리 core-admin 패키지의 요구사항과 거의 동일.
- **react-jsonschema-form (rjsf)**: JSON Schema 기반 폼 생성기, 오래되고 검증된 라이브러리지만 Zod가 아닌 JSON Schema를 직접 다루므로 zod→JSON Schema 변환 계층이 한 단계 더 필요.
- **Puck**: React용 임베드형 비주얼 드래그앤드롭 페이지 빌더(오픈소스). 0.21 버전에서 AI 페이지 생성, 리치 텍스트 편집 추가. Payload CMS와 공식 연동 플러그인(`payload-puck`) 존재. "관리자 폼"보다는 "페이지 레이아웃 빌더"에 가까워 우리 프로젝트의 "관리자 슬라이더" 요구와는 결이 다름 — 씬/레이아웃 편집 UI를 만들 때 참고할 여지는 있음.
- **Payload CMS / Refine / react-admin**: 완결형 어드민 프레임워크. Payload는 스키마 정의→자동 API+어드민 UI 생성이 강점이나 자체 서버/DB 레이어를 전제로 해 우리 Express+Drizzle+api-server 구조와 통합하려면 상당한 커스터마이징 필요. Refine/react-admin은 기존 API 위에 어드민 UI를 얹는 메타프레임워크로, zod 스키마 기반 자동 폼 생성이 핵심 기능은 아님(데이터 프로바이더 패턴 중심).

### 판단
**채택**: `zod` 내장 `toJSONSchema()` + **AutoForm(shadcn 버전)** 조합 — core-admin 패키지의 "zod 스키마→폼 자동생성" 요구를 가장 적은 코드로 만족. 우리 Tailwind+shadcn 스택과도 직접 정합.
**보류**: Payload CMS/Refine/react-admin — 완결형 어드민 프레임워크를 도입하면 자체 api-server/storage 패키지와 이중 구조가 되어 과도한 복잡도 유발(원칙 2: 심플리시티 위반). 필요 기능은 AutoForm+커스텀 admin 페이지로 직접 구현.
**관찰**: Puck — 향후 "관리자가 페이지 레이아웃 자체를 드래그앤드롭으로 재배치"하는 요구가 생기면 검토(현재 스코프 밖).

## 8. 모션/UI

### 현재 최선
- **GSAP**: 2024년 가을 Webflow가 인수, **2025-04-30부로 코어+구(舊) 유료 Club 플러그인(SplitText, MorphSVG, DrawSVG, ScrollTrigger 등) 전부 무료 전환**, 상용 이용도 표준 라이선스로 커버. 스크롤텔링(ScrollTrigger)에서 여전히 사실상 표준. 관리자 값 바인딩은 timeline API에 숫자/문자열 파라미터를 직접 주입하는 방식으로 용이.
- **Motion(구 Framer Motion)**: 2025년 Framer에서 독립, `framer-motion` → `motion` 패키지로 개명(`motion/react` import 권장). 2026-03 기준 버전 12.x, Next.js 16.x와 함께 테스트됨. React 컴포넌트 선언형 애니메이션(변수/props 바인딩)이 GSAP보다 React 친화적 — "관리자 값 바인�여" 관점에서 React 상태(zustand)와 직접 연결하기 쉬움.
- **Theatre.js**: 코드/DOM/SVG/three.js 씬을 대상으로 하는 비주얼 타임라인 기반 모션 디자인 에디터. Threlte가 공식 통합 패키지(@threlte/theatre)를 제공할 정도로 3D 씬 애니메이션에 강점. "관리자 값 바인딩" 관점에서 타임라인 자체가 이미 비주얼 에디터이므로 별도 관리자 UI 없이도 논디자이너가 다룰 여지가 있음.
- **Rive**: 상태 기반(idle/hover/pressed/loading/success/error) 인터랙티브 애니메이션, 단일 .riv 파일에 여러 상태와 전환을 포함 — 앱 상태와 애니메이션 상태를 직접 매핑하는 인터랙티브 UI(버튼, 로더)에 최적.
- **Lottie(dotLottie)**: After Effects 산출물 재생에 특화, 순수 장식적 애니메이션(아이콘, 일러스트)과 최대 호환성이 필요할 때 최선.
- **2026 업계 권고**: 아이콘/일러스트 장식용은 Lottie, 상태 기반 인터랙티브는 Rive, UI 마이크로 인터랙션은 CSS 애니메이션.

### 판단
**채택**: **GSAP(무료, ScrollTrigger 포함)** — 스크롤텔링 인터랙티브 웹의 핵심 요구와 정확히 매칭, 관리자 폼에서 숫자 파라미터(duration, ease, trigger point)를 바인딩하기 쉬움. **Motion** — React 컴포넌트 단위의 UI 트랜지션(모달, 리스트 등)에 보조적으로 채택, zustand 상태와의 선언형 바인딩이 강점.
**관찰**: Theatre.js(three-kit 씬 안에서 타임라인 애니메이션이 본격적으로 필요해지면, Threlte 사례처럼 통합 검토), Rive(상태 기반 인터랙티브 아이콘/버튼이 대량으로 필요해지면).
**보류**: Lottie — 우리 프로젝트가 AE 산출물 파이프라인을 아직 가정하지 않으므로 필요 시에만 추가.

## 9. 오디오

- **Howler.js**: 사운드 재생(효과음, 배경음) 특화. 포맷 폴백(WebM/MP3/OGG), 3D 공간 오디오, 오디오 스프라이트, 크로스브라우저 지원. 현재 버전 v2.2.3(로 언급됨, 날짜 **미확인**).

- **wavesurfer.js**: 파형 시각화 특화(플레이어/팟캐스트/오디오 에디터 UI).
- **업계 패턴**: Howler(에셋 기반 재생: 배경음, 효과음) + Tone.js(제너레이티브/리액티브 오디오 레이어)를 함께 쓰는 조합이 일반적으로 언급됨.

### 판단
**채택**: **Tone.js**(오디오 리액티브 비주얼라이저 — 주파수 분석 데이터를 three-kit 씬/모션 파라미터에 바인딩하는 우리 핵심 유스케이스와 직접 매칭) 단독 채택으로 충분. 단순 배경음/효과음 재생만 필요하면 Web Audio API 네이티브 `<audio>` + Howler를 보조로 검토.
**관찰**: wavesurfer.js — 비디오/오디오 편집 UI가 관리자 쪽에 필요해지면.

## 10. WebXR/AR

### 현재 최선
- **WebXR 브라우저 현황(2026)**: Safari 18(2024년 말, iOS/iPadOS/macOS Sequoia 동반)부터 WebXR 지원이 애플 생태계에 네이티브로 들어왔으나, **이는 주로 visionOS(Apple Vision Pro)용이며 iPhone 핸드헬드 WebXR AR은 2026년 현재도 노출되지 않음**. 즉 "모바일 사파리에서 WebXR AR 버튼"은 아직 작동하지 않는다고 봐야 함.
- **iOS 핸드헬드 AR 대안**: (1) **8th Wall** — 카메라 기반 WebAR SDK, WebXR 없이도 브라우저에서 AR 구현. (2) **AR Quick Look(USDZ)** — iOS 12+ 네이티브 지원, glTF/glb와 별도로 USDZ 모델 추가 필요. (3) **model-viewer**(구글 웹 컴포넌트) — `ar-modes` 속성으로 webxr/scene-viewer(안드로이드)/quick-look(iOS)/fallback을 자동 분기, 하나의 마크업으로 크로스플랫폼 AR 폴백 체계를 구현하는 사실상 표준 패턴. (4) **App Clip 기반 WebXR 런처** — iOS에서 더 몰입감 있는 AR이 필요할 때의 우회로.
- **8th Wall**: 유료(가격 정책이 도입 판단에 영향 — 구체적 요금제는 **미확인**).

### 판단
**채택**: **model-viewer**(간단한 3D 상품/오브젝트 뷰 + AR 폴백이 필요한 페이지에 최소 비용으로 삽입) — `ar-modes="webxr scene-viewer quick-look fallback"` 한 줄로 안드로이드(Scene Viewer)/iOS(Quick Look)/데스크톱(fallback)을 모두 커버.
**관찰**: 8th Wall — 카메라 기반의 고급 WebAR(얼굴 필터, 월드 트래킹 이펙트 등)이 로드맵에 들어오면 유료 도입 검토(tracking 패키지와 기능 중복 가능성도 함께 검토).
**보류**: 순수 WebXR Device API 직접 구현 — iPhone 핸드헬드 AR을 커버하지 못하는 한 단독 채택 불가, model-viewer/8th Wall의 폴백 계층으로만 사용.
**리스크**: iOS Safari의 WebXR 공백이 가장 구조적인 제약 — "온-액시스/오프-액시스 3D 창" 경험(항목 4)과 "AR 모드"는 별개 기술 스택으로 유지해야 함.

## 리스크 목록

1. **iOS Safari WebXR 공백**: 2026년에도 iPhone 핸드헬드 WebXR AR이 노출되지 않음. AR 기능은 model-viewer/8th Wall 폴백 체계로 별도 설계해야 하며, 오프-액시스 "3D 창" 경험(MediaPipe 기반)과 혼동하지 말 것.
2. **정확한 버전 번호 미확인**: three.js 정확한 최신 r-번호가 소스마다 r180/r184/r186으로 엇갈림(WebFetch 스냅샷이 2024년 데이터를 반환하는 등 캐시/구식 정보 혼입 가능성). 실제 채택 시점에 `npm view three version` 등으로 직접 재확인 필수.
3. **zundo 유지보수 불확실성**: npm 상 "2년 전 게시"로 표기되는 스냅샷이 있어 액티브 유지보수 여부 재확인 필요. 방치 시 대체(자체 zustand undo 미들웨어) 준비.
4. **Spark 라이선스 미확인**: 오픈소스로 알려져 있으나 정확한 라이선스(MIT/Apache/커스텀) 미확인 — 상용 배포 전 라이선스 텍스트 직접 확인 필요.
5. **인터랙티브 비디오 "끊김 없는 분기 전환" 구현 난이도**: 업계 표준 오픈소스 레퍼런스를 찾지 못함(미확인). 더블 버퍼 + 프리로드 방식을 자체 PoC로 검증해야 하며, 실패 시 Mux/Cloudflare의 자체 플레이어 SDK 기능에 더 의존해야 할 수 있음.
6. **가우시안 스플래팅 모바일 성능**: 대용량 씬(수천만~1억 스플랫)에서 저사양 모바일 기기 프레임레이트 실측 데이터 미확인 — LOD/스트리밍(Spark 2.0)이 필수 전제.
7. **Payload/Refine 등 완결형 어드민 프레임워크 배제 리스크**: 자체 AutoForm+커스텀 어드민 조합이 향후 기능(권한 관리, 감사 로그 등)이 늘어나면 재작업 비용이 커질 수 있음 — 스코프 확장 시 재평가 필요.
8. **8th Wall/Needle Engine 가격 정책 미확인**: 예산 계획 수립 전 공식 요금제 페이지 직접 확인 필요.
9. **NPM 배포 보안 정책 변화(2026-08/2027-01)**: Google의 2FA 우회 토큰 제한, 직접 배포 전환 등이 `@mediapipe/tasks-vision` 등 패키지의 향후 릴리스 프로세스에 일시적 영향을 줄 가능성.
