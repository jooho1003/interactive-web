## 0. 2026-09-13 개정 — 설계를 실제에 맞춘다

§1~§8은 첫 설계(2026-09-10)다. 작품 두 개를 만든 뒤 보니 설계와 실제가 갈라져 있었다. 이 절이 우선한다. 아래 절과 충돌하면 이 절을 따른다.

### 0-1. 무엇이 달랐나

| 설계 | 실제 (2026-09-13) |
|---|---|
| pnpm + Turborepo 루트, `apps/`·`packages/` 12개 | 루트 없음. 독립 npm 프로젝트 2개가 `projects/`에 있었다 → pnpm 워크스페이스로 묶음 (turbo는 보류) |
| 모든 앱 Vite + React + R3F | dawn-store는 Vite + React + zod. juho-lab은 무의존 ES 모듈 + three.js 벤더링 + Worker |
| 배포 1순위 Replit | juho-lab이 OpenAI Sites(Cloudflare Worker + R2)로 나갔다. Replit은 쓰지 않았다 |
| 작품만 존재 | **작품을 모아 보여주는 허브**(juho-lab)가 생겼고, 설계에 그 역할이 없었다 |
| 공용 로직은 `packages/*` | 공용 코드 0. 작품 로직은 각 앱 안에 있다 |

### 0-2. 결정

1. **앱 역할은 셋이다.**
   - **작품(work)** — 관람자가 경험하는 사이트 하나. 예: `dawn-store`. §1 스택 표와 §7 규칙은 작품에 적용한다.
   - **허브(hub)** — 작품을 모아 보여주는 스튜디오 사이트. `juho-lab` 하나뿐이다. 작품의 빌드 산출물을 `/experiences/<id>/`로 품는다. 스택 통일 규칙에서 빠진다 — 이미 호스팅 중이고 번들이 작아서 React로 옮길 이득이 없다.
   - **툴(tool)** — 작품을 찍어내는 편집기·제너레이터. 아직 없다 (`flow-editor`, `tools/new-app`).
2. **패키지는 두 번째 소비자가 생길 때 뽑는다.** 12개를 먼저 만들지 않는다. 소비자가 하나뿐인 추상화는 그 하나에 맞춰 굳고, 두 번째 작품에서 다시 뜯게 된다. 추출 트리거는 0-4 표.
3. **디렉터리는 `projects/`를 유지한다.** `apps/`로 개명하지 않는다. 작품 폴더에는 코드 말고도 `SPEC.md`·와이어프레임·시드·프롬프트가 같이 산다. 그래서 `projects/<id>/` 아래에 코드를 루트에 두거나(`juho-lab`) `app/`에 두는(`dawn-store`) 두 형태를 모두 허용하고, 워크스페이스 글롭이 둘 다 잡는다.
4. **워크스페이스는 pnpm, turbo는 보류.** 지금은 `pnpm --filter`와 루트 스크립트로 충분하다. 공용 패키지가 처음 생겨 "패키지 빌드 → 앱 빌드" 순서와 캐시가 필요해질 때 turbo를 넣는다.
5. **배포 대상은 앱마다 선언한다.** 모노레포 단일 배포 전략은 없다. 각 앱 README 첫 절에 대상·빌드 명령·산출물 경로를 적는다. 현재 juho-lab = OpenAI Sites, dawn-store = 단독 배포 없음(허브에 임베드).
6. **작품 → 허브 임베드 계약** (0-3).

### 0-3. 작품 → 허브 임베드 계약

작품은 허브의 하위 경로에서 그대로 돌아야 한다.

| 항목 | 규칙 |
|---|---|
| 마운트 경로 | `/experiences/<작품 id>/`. id는 허브 `projects.js`의 `id`와 같다 |
| 작품 빌드 | 에셋을 절대경로(`/assets/…`)로 참조해도 된다. 허브 쪽 복사 스크립트가 접두사를 붙인다. 작품 코드를 허브용으로 고치지 않는다 |
| 복사 | `projects/juho-lab/scripts/include-experience.mjs <id>`. 등록된 작품 `dist/` → 허브 `public/experiences/<id>/`, `index.html`은 "돌아가기" 헤더가 붙은 iframe 셸로 교체, 원본은 `play.html` |
| 스냅샷 | 허브 호스팅 빌드가 모노레포 밖에서 돌기 때문에 스냅샷은 git에 커밋한다. 작품을 고치면 `pnpm build:hub`로 스냅샷을 갱신하는 것까지가 작업이다 |
| 검증 | 허브 `validate.mjs`가 스냅샷 안 `story.json`·`theme.json`이 가리키는 에셋의 실재를 확인한다 |

두 번째 임베드 작품 Day Walk가 생겨 `include-dawn.mjs`를 `include-experience.mjs <id>`로 일반화했다.

### 0-5. 허브(juho-lab) 설정 계약

허브의 설정은 **누가 바꾸는가**로 층을 나눈다. 층마다 원천은 하나다.

| 층 | 원천 | 누가 바꾸나 | 저장 |
|---|---|---|---|
| 사이트 정체성 (이름·브랜드·GitHub·소개) | `public/projects.js` → `profile` | 개발자 | git |
| 작품 레지스트리 (id·제목·분류·코드 URL·라이브 URL·이미지·색) | `public/projects.js` → `projects` | 개발자 | git |
| 편집 콘텐츠 스키마·기본값·검증 | `public/content-schema.js` (`projectIds`는 레지스트리에서 파생) | 개발자 | git |
| 편집 콘텐츠 값 (문구·색·캐릭터·카메라·작품별 덮어쓰기) | R2 `museum/content.json` | 소유자 (설정 패널) | R2, ETag 낙관적 잠금, 서버가 `cleanContent`로 재검증 |
| 업로드 이미지 | R2 `media/<uuid>.<ext>` | 소유자 | R2, 5MB·25MP, SVG 거부 |
| 관람자 환경설정 (크기·확대·모션·보기) | `public/preferences.js` → localStorage `juho-village-preferences-v1` | 관람자 | 브라우저 |
| 호스팅·권한 | `.openai/hosting.json` (R2 바인딩 `MEDIA`), `server/index.js` 소유자 이메일 | 개발자 | git |
| HTML 메타 (title·description·favicon) | `public/index.html`, `public/project.html` | 개발자 | git |
| 임베드 작품 | `scripts/include-experience.mjs <id>` → `public/experiences/<id>/` | 빌드 | git 스냅샷 |

**키 규칙.** 작품 `id`가 모든 층을 잇는 키다. id를 바꾸면 R2에 저장된 작품별 편집값과 관람자 링크 설정이 끊긴다. 바꾸지 말고 새로 추가한다. localStorage·R2 키 이름(`juho-village-*`, `museum/*`)은 이름이 브랜드와 어긋나도 **바꾸지 않는다** — 바꾸면 저장된 값이 사라진다. 형식이 바뀔 때만 `-v2`로 올리고 마이그레이션을 붙인다.

**남은 문제.**
- 작품 링크의 원천이 셋이다: `projects.js`의 `url`/`liveUrl`, R2 콘텐츠의 `projects[id].link`, 관람자 설정의 `links`. 우선순위를 README에 적고, 관람자 설정의 `links`는 소유자 편집 기능이 생긴 지금 없애는 것을 검토한다.
- 소유자 이메일이 서버 코드 상수다. 호스팅이 환경변수를 지원하면 `OWNER_EMAILS`로 옮긴다 (보안 변경이라 별도 플랜).
- `og:image`·`og:title`·canonical이 없다. 사이트가 소유자 전용인 동안은 급하지 않다. 공개로 돌릴 때 채운다.
- 브랜드 표기가 흩어져 있다 (`JUHO LAB` 제목, `JUHO's village` 헤더, 편집 기본값 `JUHO`). 표기 규칙: 스튜디오 이름은 `JUHO LAB`, 허브 공간의 이름은 `JUHO's village`. 코드·패키지·폴더는 `juho-lab`.

## 1. 스택 결정

| 영역 | 선택 | 근거 |
|---|---|---|
| 워크스페이스 | **pnpm workspaces + Turborepo** | 앱 여러 개가 공용 패키지를 공유. 캐시로 빌드 시간 절약 |
| 언어 | TypeScript | 설정 JSON 스키마를 타입으로 공유해야 관리자 폼이 깨지지 않는다 |
| 프론트 | **Vite + React** | 레퍼런스 5곳 전부 이 조합. 바이브 코딩 도구(Replit Agent, Claude Code)가 가장 잘 다룬다 |
| 3D | **three.js + @react-three/fiber + drei** | A/E 패밀리. R3F로 씬을 컴포넌트화하면 레이어 패널·기즈모 구현이 쉽다 |
| 상태 | zustand | 에디터 히스토리(undo/redo)를 스토어 미들웨어로 |
| 스키마 | **zod** | API 응답 검증 + 관리자 폼 자동 생성의 단일 원천 |
| 백엔드 | **Express + Drizzle ORM** | 같은 오리진 `/api/*`. SQLite(로컬)/Postgres(배포) 스위치 |
| 스토리지 | 어댑터 패턴 (로컬 fs / Replit Object Storage / S3) | GLB·mp4는 DB 밖. 앱마다 백엔드가 달라도 코드는 같게 |
| 인증 | Clerk (선택적) | E가 Clerk 사용. 관리자 보호가 필요한 앱만 켠다 |
| UI | Tailwind + shadcn/ui | 관리자 패널 폼·슬라이더·컬러피커를 빨리 찍어낸다 |
| 배포 | ~~**Replit** (1순위) / Vercel + Railway (대안)~~ → **앱마다 선언** (§0-2 결정 5) | 허브는 OpenAI Sites(Worker + R2)로 나갔다 |

주의: Replit은 프로젝트 단위 배포라 모노레포 전체를 한 Repl에 올리면 앱마다 별도 도메인을 못 준다. **앱 1개 = Repl 1개**로 배포하고, 공용 패키지는 npm(private registry 또는 GitHub Packages)으로 배포하거나 빌드 시 번들에 포함한다. 자세한 건 §6.

## 3. 공용 패키지 상세

### 3-1. `config-schema` — 모든 것의 원천
레퍼런스 API 응답을 그대로 zod로 옮긴다. 스키마가 곧 문서이자 관리자 폼이다.

```ts
// packages/config-schema/src/responsive.ts
export const responsive = <T extends z.ZodTypeAny>(s: T) => z.object({ desktop: s, mobile: s });

// packages/config-schema/src/scene.ts  (패밀리 A — digital-figures /api/objects 그대로)
export const SceneObject = z.object({
  id: z.string().uuid(), name: z.string(), spaceId: z.number(),
  positionX: z.number(), positionY: z.number(), positionZ: z.number(),
  rotationX: z.number(), rotationY: z.number(), rotationZ: z.number(),
  scaleX: z.number(), scaleY: z.number(), scaleZ: z.number(),
  castShadow: z.boolean(), receiveShadow: z.boolean(), flatShading: z.boolean(), visible: z.boolean(),
  materialEnabled: z.boolean(),
  matMetalness: z.number().min(0).max(1), matRoughness: z.number().min(0).max(1),
  matGlass: z.number(), matColorIntensity: z.number(), matTextureContrast: z.number(),
  matTextureGamma: z.number(), matReflectionIntensity: z.number(),
  matGlassMode: z.boolean(), matGlassIor: z.number(), matGlassRoughness: z.number(),
  createdAt: z.string().datetime(),
});

export const PortalSettings = z.object({ globalSensitivity: z.number(), xSensitivity: z.number(), /* ... */ });
export const LightSettings  = z.object({ intensity: z.number(), fogEnabled: z.boolean(), /* ... */ });
export const SpaceConfig    = z.object({ portalSettings: PortalSettings, lightSettings: LightSettings,
```

### 3-2. `core-admin` — 관리자 셸
- 좌측 탭: 앱이 등록한 섹션 (예: 포탈 / 조명 / 오브젝트 / 디자인 / 자막 / 앱 정보).
- 스키마→폼 렌더러: number→슬라이더(min/max 있으면) 또는 입력, hex→컬러피커, boolean→토글, enum→셀렉트, `responsive()`→desktop/mobile 탭.
- 공통 버튼: 저장 / 이전 저장본 불러오기 / JSON 내보내기·가져오기 / 초기화. 섹션마다 on/off 토글 + 리셋 (OSF 방식).
- **Design Check**: 저장된 설정값과 현재 DOM의 계산값을 대조해 "All matched" / 불일치 항목을 표시 (OSF 관리자에서 확인된 기능).
- **다중 프리뷰**: Desktop(672px) / Mobile(375px) / Email 을 나란히 띄우고 슬라이더로 실시간 조정 (OSF Scheduling Design 방식).
- **Quick Edit는 `inline-editor`로 이관** (§3-3). 관리자 폼은 "설정 목록을 위에서 아래로", 툴바는 "화면에서 직접" — 두 입구가 같은 저장소를 본다.
- **오버라이드 탭**: 툴바가 만든 스키마 밖 수정값의 목록·고아 감지·스키마 승격 (§3-3-5).
- **앱 정보 탭 (필수)**: 타이틀, 파비콘, OG 이미지, 도메인, 제작자 링크, 저작권 문구, `secretCode`/`nextWorkHint`(이스터에그 체인). minikingdom 타이틀 사고 방지.
- 노출 모드: `ADMIN_MODE=public | auth | hidden`. A처럼 공개, B처럼 로그인 뒤, 또는 URL `/admin`만. **납품용은 `auth` 강제** — 어드민은 클라이언트와의 소통 레이어다 (06 §5).

### 3-3. `inline-editor` — 편집 툴바 (인앱 직접 편집)

`core-admin`이 "설정 목록을 폼으로 편집"이라면, `inline-editor`는 **작품 화면 위에서 요소를 직접 클릭해 고친다**. 레퍼런스 DYW의 톱니 설정 패널이 이 자리다. 단 DYW는 그 패널이 **무인증으로 열려 있어 누구나 라이브 콘텐츠를 바꿀 수 있다** — 08 §5가 결함으로 지적한 지점이다. 기능은 베끼되 게이트는 `ADMIN_MODE` 하나로 통일한다.

설계 근거는 전사에 있다.
> "얘도 바이브 코딩으로 이런 **우측 상단**에 **관리자만 볼 수 있는 세팅창**을 만들었어요. (…) 이걸 매번 AI랑 소통하면서 할 수 없으니까 제가 직접 할 수 있는 공간을 만든 거죠." (`docs/transcripts/02-게임-영화-툴-시연.txt:174`)

> "좀 **귀찮아서** 나중에 퀵 에디시라고 **지금 이 화면에 있는 메뉴만** 바로바로 할 수 있는 기능도 넣기도 하고" (`02-게임-영화-툴-시연.txt:279`)

두 번째 인용이 이 패키지의 존재 이유다. **관리자 패널이 이미 있는데도** Quick Edit가 나중에 추가됐다. 없던 기능이 필요해서가 아니라 **지금 보고 있는 것에 도달하는 시간** 때문이다. 그래서 §3-3-4의 제1 규칙이 나온다.

#### 3-3-1. 편집 모드
- 진입: 인증 통과 후 `?edit=1` 또는 단축키. 툴바는 **동적 import** — 관람자 번들에 편집기 코드를 넣지 않는다 (04 §5 성능 예산).
- 화면 위 두 겹: **선택 하이라이트 레이어**(포인터 이벤트 가로채기) + **툴바**(**우측 상단** 고정, 접기·드래그 이동 가능). 위치는 취향이 아니라 레퍼런스 실물과 맞춘 것이다 — 하단은 모바일에서 자막·컨트롤과 겹친다.
- 뷰포트 스위치: 툴바의 `Desktop / Mobile` 토글. 지금 어느 쪽을 고치는지 배지로 항상 표시하고, 값은 그쪽에만 쓴다 (§7 규칙 3).

#### 3-3-2. 하이브리드 바인딩 — 두 저장 경로
클릭한 요소를 두 단계로 해석한다.

| 경로 | 조건 | 저장 위치 | 성격 |
|---|---|---|---|
| **스키마 경로** | 요소에 `data-edit="<zod 경로>"` | `app-settings` / `theme` / `story` 의 해당 필드 | 정식. 타입 검증·마이그레이션·이전 저장본이 전부 딸려온다 |
| **오버라이드 경로** | 바인딩 없음 | `overrides` (별도 설정 키) | 임시. 추적·승격 대상 (§3-3-5) |

툴바 좌측에 **출처 배지**를 항상 띄운다: `[스키마 intro.desktop.titleText]` / `[오버라이드 · 자동치유됨]`. 지금 고치는 값이 어디로 가는지 모르는 채로 편집하게 두지 않는다.

앱 쪽 바인딩 API:
```tsx
<Editable path="intro.desktop.titleText" eid="intro-title" as="h1">{t.intro.title}</Editable>
// → <h1 data-edit="intro.desktop.titleText" data-eid="intro-title">…</h1>
```
`data-eid`는 셀렉터가 아니라 **안정 ID**다. 컴포넌트를 옮기거나 감싸도 유지된다.

#### 3-3-3. 오버라이드의 셀렉터 문제와 자동 치유
`nth-child` 셀렉터는 코드가 바뀌면 조용히 빗나간다. 그래서 오버라이드는 셀렉터만 저장하지 않고 **지문**을 함께 저장한다 (스키마는 §3-1 `Override`).

재적용 순서: `eid` → `selector` → 지문 fuzzy 매칭. 지문으로 찾으면 셀렉터를 갱신해 다시 저장하고(`status: 'healed'`) 배지에 표시한다. 셋 다 실패하면 **버리지 않고 `orphan`으로 남겨** 관리자에 경고를 띄운다. 조용한 소실이 가장 나쁘다.

#### 3-3-4. 툴바 패널 (선택 요소 타입별)

**제1 규칙 — 툴바에는 지금 화면에 보이는 것만 올린다.** 전체 설정 목록을 툴바에 넣는 순간 `core-admin`과 같아지고, 툴바가 존재할 이유(탐색 비용 0)가 사라진다. 화면에 없는 값을 고치려면 관리자 폼으로 간다.

**제2 규칙 — 수치는 슬라이더가 기본, 숫자 입력은 보조.** 시안을 맞추는 작업은 값을 아는 게 아니라 보면서 맞추는 것이다.
> "그대로 바이브 코딩한테 요청하니까 좀 비슷한데 다르게 만들더라고요. 그래서 **슬라이드 컨트롤러 만들어 달라고 하고 제가 여기서 직접 수정하면서 최종 디자인을 아주 똑같이** 만들 수 있었습니다" (`03-OSF-클라이언트-시연.txt:40`)

| 대상 | 컨트롤 |
|---|---|
| 텍스트 | 인라인 편집(더블클릭 → `contentEditable`), **언어 탭 `ko`/`en`** — 한쪽만 채우면 저장 시 경고. 크기·굵기·자간·행간·정렬 |
| 색 | **팔레트 우선**: `masterColor`(기본/포인트/그레이) → `savedColors[]` → 자유 hex. 자유 hex를 쓰면 "저장색으로 추가"를 권한다. 마스터 색 변경은 `colorMasterRefs`에 걸린 키를 전부 따라 바꾼다. UI 요소는 **normal / highlight / disabled 3단을 한 세트로** 노출한다 — 하나만 바꾸면 나머지 둘이 어긋난다 |
| 폰트 | **UI 킷이 정의한 세트**에서만 선택. 임의 폰트명 입력 금지 — 로딩 안 된 폰트로 깨지고 통일성도 무너진다. 04 §5의 서브셋 예산 안에 든 것만 목록에 오른다.<br>> "여기에 들어간 **폰트도 어울리게 이렇게 킷으로** 만들어달라고 하면 통일성 있는 킷으로 폰트가 제작이 됩니다" (`02-게임-영화-툴-시연.txt:74`) |
| 이미지 | 드래그앤드롭 교체 → `storage` 업로드 → `asset-pipeline` 규격 변환 → 캐시버스팅 URL을 `media.src`(또는 오버라이드 `src`)에 기록. `objectFit: cover \| contain`, `alt` |
| 핫스팟 | 영상·이미지 위에 **드래그로 사각형**을 그려 좌표(%)를 잡는다. DOM 셀렉터가 아니라 좌표라 오버라이드 경로를 타지 않는다 — 항상 스키마(`hotspot {x,y,width,height}`)에 쓴다. 표시 시간창(`startTime`/`endTime`), 디버그 표시 토글 |
| 박스 | 배경색·투명도, 여백, 반경, 테두리 |
| 공통 | undo/redo(`zundo`), 이 요소만 초기화, 저장, 편집 종료 |

이미지 교체가 성립하려면 **에셋 경로가 데이터에 있어야 한다.** 레퍼런스(A/B)는 노드 id → 파일 경로가 암묵 규약이라 교체 지점이 없다. 첫 작품 `dawn-store`의 `node.media.src`처럼 **명시 문자열**을 표준으로 삼는다 (08 §4).

#### 3-3-5. 오버라이드는 빚이다 — 승격 경로
오버라이드가 쌓이면 "이 값이 어디서 왔나"를 아무도 모르게 된다. 그래서 갚게 만든다.
- `core-admin`에 **오버라이드 탭**: 개수·대상·수정 시각·`status` 목록.
- 각 항목에 **"스키마로 승격"** 버튼: `config-schema`에 붙일 zod 필드 스니펫과 컴포넌트에 넣을 `<Editable path=…>` 스니펫을 생성한다. 개발자가 코드에 반영하면 그 오버라이드는 소멸한다.
- CI 게이트: 앱당 오버라이드 20개 초과면 빌드 경고, `orphan`이 하나라도 있으면 실패. 07 §4의 "규칙은 70%만 지켜진다 → 코드 게이트로 강제"에 해당한다.

승격 버튼은 새로운 발명이 아니라 원래 손으로 하던 일의 자동화다.
> "저는 주로 이렇게 이곳에서 **직접 제가 컨트롤 할 수 있는 옵션들을 계속 추가하면서** 만들어 달라고 해요" (`02-게임-영화-툴-시연.txt:31`)

오버라이드는 "컨트롤이 아직 없는 값"이고, 승격은 그 값에 컨트롤을 붙이는 행위다. 그 요청을 프롬프트로 매번 치는 대신 버튼으로 만든 것.

#### 3-3-6. 경계 — DOM 전용
`inline-editor`는 **DOM 레이어만** 다룬다. three.js 캔버스 안의 오브젝트는 셀렉터가 없으므로 `three-kit`의 기즈모·레이어 패널이 담당한다 (§3-5). 툴바는 두 편집기를 상단 모드 탭(`DOM / 3D`)으로 묶어 하나로 보이게 하되, **코드는 섞지 않는다.**

### 3-4. `api-server` — Express 팩토리
```ts
createApiServer({
  settings: { 'app-settings': AppSettings, 'video-flow': VideoFlow, 'overrides': Overrides },  // GET/PUT /api/<key>
  collections: { objects: SceneObject },                                // CRUD /api/objects?space=
  uploads: { glb: { maxMB: 20, accept: ['.glb'] }, video: { maxMB: 500 } },
  auth: clerkGuard | none,
  storage: storageAdapter,
});
```
- 항상 제공: `GET /api/saved-at`, `GET /api/health`, 캐시버스팅 `?v=`.
- 설정은 버전 테이블에 append → "이전 저장본 불러오기"가 공짜. 툴바 저장도 같은 경로를 타므로 인라인 편집에도 되돌리기가 그대로 붙는다.
- 툴바 저장은 디바운스 + 낙관적 반영. 버전 행에 `source: 'admin' | 'toolbar'`를 남겨 누가 어디서 바꿨는지 추적한다.

### 3-5. `three-kit` — 패밀리 A 심장
- `<SceneShell>`: 캔버스, 조명(LightSettings 바인딩), 안개, 포스트프로세싱(glow).
- `<GLBObject object={SceneObject}>`: 로더 + 머티리얼 오버라이드(metalness/roughness/glass/gamma) + 그림자 플래그.
- `<Gizmo>`: drei `TransformControls` + 멀티 선택 일괄 스케일.
- `<LayerPanel>`, `<HistoryPanel>`: zustand + `zundo`.
- 로딩: Draco 디코더, KTX2 텍스처, 프로그레스 바. **성능 예산은 04 가이드 §5.**

### 3-6. `tracking` — 오프-액시스
- MediaPipe FaceLandmarker(WASM)로 얼굴 중심 (x, y, 크기→z 근사).
- `useOffAxisCamera(portalSettings)`: 감도·스무딩·flip·eyeDistance를 PortalSettings로 바인딩. `PerspectiveCamera.setViewOffset` 기반.
- 폴백 체인: 카메라 권한 거부 → 마우스 → (터치) 자이로.
- 제약 명시: 얼굴 1명만. 2명 이상이면 가장 큰 얼굴만 채택.

### 3-7. `video-kit` — 패밀리 B 심장
- `<BranchingPlayer flow={VideoFlow} settings={AppSettings} lang="KO">`
- 그래프 엔진: 현재 노드, 플래그 Set, `glowCondition` 평가, `isEnding` 처리, 히든 노드.
- 프리로더: 다음 후보 노드 2~3개를 `<video preload>`로 미리. 포스터 png 지원.
- 자막 엔진: `mm:ss(.ms)` 파싱, fadeIn/out, desktop/mobile 스타일.
- 오디오: BGM 루프 + 언어별 더빙 mp3를 영상과 동기(`currentTime` 보정).
- 화살표 버튼: `ArrowDesign` 바인딩, 효과음, 글로우 애니메이션, `buttonShowTiming`.
- 확장 슬롯: hotspot, questionMenu, quickJump (C에서 확인된 기능).

### 3-8. `flow-editor` — 패밀리 B의 기획 층
- 캔버스: 노드(장면 이미지 + 라벨), 엣지(선택지 텍스트 / Dashed / Bridge), `Tab` 자식·`Enter` 형제, 서브 캔버스(노드 안 캔버스).
- 생성 훅: 노드에서 Generate Image, 두 노드 사이에서 Start/End 프레임 영상 생성 (외부 API 어댑터, 크레딧 표시).
- 출력: `VideoFlow` JSON + 미디어 매핑 → `branching-movie` 앱이 그대로 읽는다.
- 저장: 프로젝트 = 디스크 1장 메타포. 앱마다 컨셉 스킨을 씌울 수 있게 렌더러와 데이터 분리.

### 3-9. `integrations`
- `notion`: 구독자·예약·설정을 Notion DB로 미러링 (클라이언트가 노션에서 본다).
- `gcal`: 일정 읽기/쓰기, 알람.
- `email`: Welcome/확인 메일 템플릿(관리자에서 편집) + 발송.
- `youtube`: 최신 영상 RSS → 썸네일 자동 생성.
- `wallet`: wagmi/RainbowKit 지연 로드, ENS 표기, 거래 원장 캐시.

### 3-10. `sync`
- `useSavedAt(intervalMs)`: 서버 `saved-at` 변경 감지 → 토스트 "다른 곳에서 저장됨, 새로고침?".
- BroadcastChannel로 같은 브라우저 탭 간 즉시 반영.

## 5. 템플릿 제너레이터

```bash
pnpm new portal-space my-gallery --title "MY GALLERY" --domain my-gallery.replit.app
```

템플릿은 앱의 "완성된 최소 상태"를 유지한다. 새 공용 기능이 생기면 템플릿도 갱신.

## 6. 배포 전략

### 6-1. Replit (권장, 강연자와 동일)
- 앱 1개 = Repl 1개. 모노레포에서 `pnpm --filter my-gallery deploy` 실행 시:
  1. `pnpm --filter my-gallery build` (공용 패키지는 Vite가 번들에 포함, 서버는 `tsup`으로 단일 파일)
  2. `dist/` + `server.js` + `.replit`을 Repl 저장소에 push (Repl은 GitHub 연동)
- Replit Object Storage를 `storage` 어댑터로. DB는 Replit PostgreSQL.
- 장점: 핸드폰에서 Replit Agent로 즉흥 수정 가능 (강연자 워크플로우). 단점: 모노레포 인식 못 함 → 빌드 산출물만 보낸다.

### 6-2. Vercel + Railway (대안)
- 프론트: Vercel 모노레포 프로젝트(루트 디렉터리 `apps/<name>`).
- API: Railway/Fly에 `api-server`. CORS 대신 Vercel rewrite로 `/api/*` 프록시 → 레퍼런스와 같은 same-origin 유지.
- 영상·GLB: Cloudflare R2 (egress 무료). 큰 영상 파일이 많은 패밀리 B에 유리.

### 6-3. 공통
- 도메인: `*.replit.app` 기본, 클라이언트 납품은 커스텀 도메인 (gryun-aimovie.com처럼).
- 미디어 캐시: `Cache-Control: immutable` + `?v=timestamp`.
- 관리자 보호: 납품용은 `ADMIN_MODE=auth` 강제. 공개 에디터(A 방식)는 데모 전용.
- **편집 툴바도 같은 게이트**: `/admin`과 인앱 툴바의 보호 수준을 분리하지 않는다. 게이트가 둘이면 하나는 반드시 열린 채로 남는다 (DYW 사례, 08 §5). 툴바 번들은 인증 후 동적 로드.

## 7. 개발 규칙

1. **새 기능은 스키마부터.** `config-schema`에 필드 추가 → 관리자 폼 자동 생성 → 그 다음 렌더링.
2. **같은 3D/비디오 로직을 두 앱에 복사하지 않는다.** 첫 작품은 앱 안에 로직을 둬도 된다. 두 번째 작품이 같은 로직을 쓰는 순간 `three-kit`/`video-kit`으로 추출한다 (§0-4). 허브는 이 규칙에서 빠진다.
3. **desktop/mobile 두 벌은 기본.** `responsive()`를 안 쓴 UI 설정은 리뷰에서 반려.
4. **폴백 없는 입력 금지.** 카메라·마이크·지갑·자이로는 반드시 대체 경로.
5. **성능 예산 초과 시 머지 금지.** 04 가이드 §5 수치 기준. CI에서 `dist` 크기와 GLB 총량 체크.
6. **템플릿 갱신은 별도 PR.** 앱에서 검증된 기능만 템플릿으로 올린다.
7. **화면에 보이는 값은 툴바로 고칠 수 있어야 한다.** 새 UI 요소를 만들면 `<Editable path=…>`로 감싸거나, 왜 감쌀 수 없는지를 PR에 적는다. 스키마 리프 필드가 관리자 섹션·툴바 어느 쪽에도 안 걸리면 스냅샷 테스트가 실패한다 (07 §4).
8. **오버라이드는 빚이다.** 스키마 밖 수정은 임시 허용이지 정착지가 아니다. 앱당 20개 초과 시 경고, `orphan` 발생 시 빌드 실패. 반복해서 고치는 값이면 스키마로 승격한다 (§3-3-5).
9. **에셋 경로는 데이터에 둔다.** 노드 id에서 파일 경로를 암묵 계산하지 않는다. 경로가 데이터에 없으면 툴바로 이미지를 바꿀 수 없다 (§3-3-4).
